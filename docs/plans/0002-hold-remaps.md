## Decisions (Joel, 2026-10-10, answering the first draft)

1. **A hold remap is a parent in the app group's command tree; its children are commands** (F9 "Structure"). It sits beside the group's commands and categories in Commands › Apps; selecting it shows its form (hold key, tap time, active, Use on) in the side panel; the commands under it are ordinary commands whose trigger is an **input** (a button, a set of buttons, a wheel direction, a key) and whose steps are either one **Remap** step (held through; the common case) or ordinary steps run at the press. No Global hold remaps for now; no hold-time threshold for letter hold keys.
2. **Hold keys may not be Ctrl, Alt, Shift, Win/Cmd or Fn.** Those are already "while holding" keys of triggers (F1), and the After-key logic owns them.
3. *(Dropped: "a row points at an existing command". With decision 1 a hold remap's children are commands themselves, so nothing needs pointing at. A step that runs another command can come later as a step type if Joel ever wants one.)*
4. **Any mouse button or wheel turn cancels the tap**, an input of the hold remap or not (Joel: "if a mouse button is pressed while space is held then no space will be sent"). Moves never do. Ctrl/Alt/Shift/Win pressed during the hold pass through and do not cancel it, so Shift held across a Space tap gives Shift + Space.
5. **Instant foreground** (Joel: "instant might be needed"): the platforms report a new foreground app, and the watch answers at once instead of at its 200 ms poll (step 3).
6. **One hold remap active at a time.** Another hold key pressed while one is held is an ordinary input of the active one.
7. **Button sets match exactly.** The output held is the Remap command whose button set equals the input buttons held right now; none → nothing held. On a change: release the old output first, then press the new one.
8. **The hold key belongs to the foreground app**, decided at its press; inputs pressed during the hold use that decision, even over another app's window on a second display.

## Design

### Core

Modelled the way categories are (they are the nearest thing: a parent in the tree with its own form, `UseOn`, rules and sync item), but a type of its own, since a hold remap changes what its commands' triggers mean.

| Type | Where | Role |
|---|---|---|
| `HoldRemap`, `HoldRemapId` | `Core/HoldRemaps/` (new, README) | `Id`, `Name` (defaults to the hold key's name, renameable), `HoldKey` (`KeyCode`), `TapTimeMs` (default 180), `IsActive`, `UseOn`. On `AppGroup.HoldRemaps`, sorted by name, empty by default |
| `Command.HoldRemapId` | `Mapping/Command.cs` | the hold remap a command belongs to, as `CategoryId` names its category (null = an ordinary command); a command in a hold remap has no category |
| `Trigger.InputTrigger(HoldInput)` | `Mapping/Trigger.cs` | the trigger of a command in a hold remap; `HoldInput` = `Buttons(HeldButtons set)` / `Wheel(WheelDirection)` / `Key(KeyCode)`; `Describe` ("Left + Right", "wheel up", "W"); never matches a `PressedTrigger`, so the resolver never fires it for a gesture or wheel press |
| `Remap` step type | `Core/Steps/Remap/` (vertical slice, N3) | `Output`: `Button(MouseButton, KeyModifiers)` (modifiers around the down only) / `Key(KeyCode, KeyModifiers, rightHand)` (modifiers held for the whole press) / `Wheel(ScrollDirection, KeyModifiers)` (wheel inputs only); conversion rule **same on both** (a platform version gives another output where needed, F8); declared as offered only in hold remaps, so the step picker shows it there and nowhere else; the executor never runs it (the worker does, below), so its `Execute` reports skipped |
| `HoldRemapRules` | `Core/HoldRemaps/` | called by `MappingRules`: hold key not a modifier; hold keys and hold remap names unique per group; an `InputTrigger` only on a command in a hold remap and only that trigger there (or `None` while unbound); inputs unique per hold remap (two hold remaps may both use Left); a Remap step is a command's only step; a wheel input takes a Wheel or Key output; used on at least one platform; a command whose `HoldRemapId` names nothing is moved to the group's ordinary commands, never refused |
| `HoldRemapPlan` | `Core/HoldRemaps/` | what the hook needs for one app group on this platform, built off the hook thread: per hold key its tap time and its inputs as bit sets (buttons, wheel directions, a 256-bit key set). Immutable; the hook reads it through one volatile reference |
| `HoldRemapMachine` | `Core/HoldRemaps/` | the behaviour, pure and table-tested; the worker runs it as it runs `CaptureStateMachine`. Events `HoldDown`, `HoldUp`, `Button`, `Wheel`, `Key`, `Rollover`, `Reset`, each with its timestamp; outcomes `TapHoldKey`, `PressOutput`, `ReleaseOutput`, `WheelOutput`, `ReplayKey`, `RunSteps(commandId)`. Owns the tap decision, the rollover, rolling between button sets (decision 7) and the pairing of every output down with its up, also across `HoldUp` before the buttons and across `Reset` |

The resolver skips commands in a hold remap. `MappingStore`: add, update, remove a hold remap (one undo step each; removing one asks, then removes its commands, as deleting a group does); commands go in and out through the existing command mutators. `KnownApps` learns `Blender.exe` ↔ `Blender` (Platform.MacOS README, ignore-list check 5).

### Config and sync

`holdRemaps` on a group and `holdRemap` on a command in the config file (omitted when empty or null); the Config README documents the members. Sync: a new item kind `holdRemap:<groupId>/<id>` for the header (name, hold key, tap time, active, Use on), keyed as categories are; its commands travel as command items carrying `holdRemap`. Raise `SyncFile.CurrentFormatVersion` to 11 (a format 10 build would drop the hold remaps and publish the group without them, and could not read an input trigger or a Remap step) and, if the reader needs it, the config schema, with the comment lines those constants carry.

### Engine: the hook thread (`Engine/Input/HoldRemapShadow`, called from `InputGate.Handle`)

The hook's copy of the facts it needs to answer "suppress?" for hold remaps, as `SuppressionShadow` is for gestures; single writer, no allocation beyond the one message, no window lookup (invariant 1). Asked **before** the gesture shadow, so an input of the held hold remap never reaches gesture capture even when it is the stroke button.

- **Hold key press:** claimed (suppressed, and owed with its repeats and release in `KeySuppressionShadow`, which gets a general "claim this press" input besides its modifier claim) iff the published plan has this key, the engine is enabled, not paused by a focused app, the ignore key is up, no hotkey capture is armed, no gesture press is owned, no hold is active, and this is a fresh press (not a repeat of a press the OS saw). The "over an ignored app" bit does **not** stop it: Joel's Blender is on the ignore list in that mode (plain Middle keeps navigating there) and must keep its hold remap.
- **While held:** an input button's down is suppressed and owed (its up suppressed whatever the hold does meanwhile); an input wheel turn is suppressed; an input key's press is claimed. A key that is no input, within the tap time and before anything was used, is the rollover: claimed, and the worker sends the hold key's tap and then **replays** that key's press; its repeats and release are suppressed and replayed too (a `replayed` key set in the shadow). Everything else follows the existing paths.
- **Messages:** one `WorkerMessage.Hold(...)` per decision, critical like a button. A message that cannot be enqueued undoes the decision (the shadow's `Save`/`Restore` pattern), except a release, which is still consumed.
- **The hold key's release** while a key-repeat-less hold outlives `KeySuppressionShadow.LostReleaseAfterMs` (2 s): the hold must still own it. Decide in step 3 with a test (macOS can have key repeat off; Space is held through long orbits).

### Engine: the watch, the platforms and the worker

- **Foreground answer.** `IgnoreListWatch` (and `IgnoreLookup`) also watch focus while any active hold remap can match on this platform, find the foreground's app group when `ForegroundKey` changes, and publish its `HoldRemapPlan` (`InputGate.PublishForeground`).
- **Instant (decision 5).** `SystemEventKind.ForegroundChanged`, raised by `Win32SystemEvents` from `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)` on the thread that pumps for it (the UI thread today; its own pump thread if that ever proves slow), and by a new `MacSystemEvents` from `NSWorkspaceDidActivateApplicationNotification` (the same class gives macOS the sleep, wake and display events the Platform.MacOS README lists as not built). The watch wakes on it and checks focus at once; the 200 ms poll stays as the backstop.
- **Worker.** `EngineWorker` runs the `HoldRemapMachine` and cross-checks every hook decision against it (Warning on a mismatch, as for capture). It injects Remap outputs itself (low latency, in order with the input): a button output as Ctrl/Shift… down, `Press(button, x, y)` at the event's position, modifiers up; a key output with its modifiers held through the press; a wheel output through `Scroll` (claimed by `OwnWheelInjections`). `RunSteps` goes to the `CommandExecutor` as an `ExecutionRequest` for that command, target the foreground window. `ResetMachine` and engine stop release every held output (A19).
- **Log source `hold`:** Info when hold remaps start or stop being watched; Debug per hold (`Hold`, key, app, then `Tap sent` / `Tap not sent` with the held time and why, `Rollover` with the key, `Output` changes); Warning for a failed injection. Engine README: the thread table, a "Hold remaps" section, the log table; `docs/reference/threading.md` if it lists the hook's work.

### App

Wireframe first (ADR-0002 §5b), reusing what categories already have in `Components/CommandTree` (`SectionRow`, the side-panel form):
- **Tree:** an app group shows its hold remaps as parent rows beside its categories ("Space · hold remap"), their commands under them. Right-click on a group: **New hold remap**; on a hold remap: New command, Rename, Delete, Copy, Paste.
- **Hold remap form** (side panel): name, hold key (the hotkey capture field in one-key mode, refusing modifiers), tap time (ms), active, Use on. Header text: "Hold remaps — remap inputs or run commands while a key is held".
- **Command under a hold remap:** the header's trigger area shows **Input** instead of the gesture picker: buttons by detect-to-assign (several for a set), wheel up/down, or a key by the capture field. The step list offers the Remap step (button / key / wheel output, modifier toggles) besides the ordinary types.

## Steps

0. **macOS spike: done 2026-10-10**, [learnings 0005](../learnings/0005-hold-remaps-mac.md); the spike is deleted. Findings: the hold key and the tap need nothing Mac-specific; a button output's modifiers must be posted through CoreGraphics (flagsChanged events around the down, the flags on the mouse down); and while a button output is held the physical drags must be swallowed and re-posted as Middle drags (right-drags do not move a posted Middle drag). That is step 3a.
3a. **macOS posting (from step 0).** In `Platform.MacOS`, button outputs with modifiers and held-drag re-posting through CoreGraphics behind `IInputSimulator`; in the engine, while a hold remap holds a button output on a platform that asks for it, the hook swallows moves and drags and the worker re-posts them. Windows unchanged. **Built 2026-10-10, compiled, not yet run on a Mac:** `IInputSimulator` gained `PressRemapButton` / `ReleaseRemapButton` / `DragRemapButton` and `RepostsRemapDrags`; `MacRemapButtonSimulator` posts them through CoreGraphics; the machine has a `Move` event and a `DragOutput` outcome; the checks are in the Platform.MacOS README ("Hold remaps: posting on macOS").
1. **Core** (`Core/HoldRemaps/`, `Steps/Remap/`, the trigger, `Command.HoldRemapId`, `AppGroup.HoldRemaps`, rules, store, `KnownApps` pair, READMEs). Tests: rules; the machine against tables written from Joel's words: tap at 179 / 181 ms, a click inside a short Space (no tap), a long Space with nothing (no tap), rollover "a b", Shift across a tap, rolling Left → Left + Right → Right → Left + Right → Left with the exact output sequence, Space released before the buttons, Reset with outputs held, a Steps command fired once per press.
2. **Config and sync.** Reader/writer, round-trip, an older file reads as no hold remaps, the format-version guard, a three-way merge of hold remap and hold-remap command items.
3. **Engine and platforms.** `HoldRemapShadow`, `KeySuppressionShadow` claim, `InputGate` order, the watch publishes the foreground plan, `ForegroundChanged` on both platforms (`MacSystemEvents` new), worker runs and injects, executor for Steps commands, logging, READMEs. Tests (fakes only, never a real hook): a randomized pairing test in the style of `ChordPairingTests` (hold keys, input and non-input buttons, the stroke button, keys, wheel; models the OS from passed events plus injections; asserts nothing is ever held at the end and every hook decision equals the machine's), and `EngineHarness` end-to-end cases for each Joel scenario.
4. **App.** Tree, hold remap form, Input picker, Remap step form, dev-gallery entry.
5. **Joel's Blender, Mac then PC.** The lead creates the Blender app group (`blender.exe` / `Blender`) and its Space hold remap with the commands Orbit (Left → Middle), Pan (Right → Shift + Middle), Zoom (Middle → Ctrl + Middle), Zoom both (Left + Right → Ctrl + Middle), Grab (W → G), Scale (E → S), Rotate (R → Ctrl + Shift + Alt + R), Frame (F → Numpad .), through the UI or in `augram.json` (app stopped, file backed up), tells Joel, he runs the "Done when" list. The lead runs the app only after saying so (CLAUDE.md). Then the session handoff, and the AutoHotkey script retires.

## Not in this plan

Global hold remaps; a hold-time threshold for letter keys; re-posted drags on macOS for a **key** input held as a button output (W → Middle: step 3a covers button inputs only); a step that runs another command; leader-key sequences (tap Space, then W); marking-menu style radial menus; hold keys that are modifiers.
