# Learnings 0001: spike 2 (risks B1–B4)

**Status: PARTIAL** — self-verified parts recorded 2026-10-05; Joel's interactive runs pending. Code: `src/Augram.Spike2` (throwaway; delete when M1 starts). Run: `dotnet run --project src/Augram.Spike2 -c Release -- <activate|overlay|hook|keys>`; see its README for options and pass/fail criteria.

Dev machine: one 3840×2160 monitor at 125 %, Windows 11, .NET 10.0.5 runtime, SharpHook 7.1.3, Avalonia 11.3.22, PerMonitorV2 DPI awareness via app.manifest (hook, cursor and window coordinates all physical pixels).

## B2 overlay (Avalonia transparent window) — VERIFIED on one monitor, game and multi-DPI pending

| Variant | First segment rendered after button-down | Next frame callback |
|---|---|---|
| hidden when idle, `Show()` per stroke | 3.3–11 ms (first stroke of the process is the slow one; later 3–4 ms) | 11–20 ms (one 82 ms outlier on the very first stroke) |
| kept shown but empty (`keep`) | 0.3–6 ms | 7–11 ms |
| `WS_EX_LAYERED` added (`layered`) | same as default | same |

- Per-batch render 0.01–0.13 ms average, max ~4 ms (first render only). Worst hook-handler time 0.4 ms (invariant 1 holds).
- The overlay **never became the foreground window** (polled every 250 ms). `ActualTransparencyLevel = Transparent`. Ex-style after fix-up: `TOPMOST | TOOLWINDOW | TRANSPARENT | NOACTIVATE | NOREDIRECTIONBITMAP`.
- **Avalonia `Show()` rewrites `GWL_EXSTYLE`** and drops `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` on every re-show. Re-applying them immediately after `Show()` restores them. The real `IOverlay` must either re-apply after every `Show()` or keep the window shown-and-empty (which is also the lower-latency variant). **Decision for M1 (revised 2026-10-06 after two incidents): the overlay is hidden whenever no stroke is in progress.** It is shown on stroke begin only after the ex-style has been re-applied and read back as click-through; if verification fails it stays hidden and the trail is a no-op with an Error in the log. A watchdog hides it if it is visible for 3 s without a stroke. Reason: an unverified full-screen window on top swallows every left click system-wide, which happened twice on 2026-10-06 when agents launched the app; "shown and empty" turned a bug into a lockout. 3–11 ms to the first segment is within one frame and acceptable. This also avoids SP.net's "hook window counts as visible" fullscreen-game problem (reference §9, 0.5.6.3).
- `Window.Opened` fires on every `Show()` after a `Hide()`, not just the first; one-time setup needs its own flag.

## B4 keyboard — media keys and text VERIFIED, system-wide suppression pending

- SharpHook `SimulateKeyPress` for VolumeUp/VolumeDown/MediaPlayPause returns `Success` and the hook sees VK 0xAF/0xAE/0xB3. Media key step: use SharpHook, no Platform call needed.
- `SimulateTextEntry("augram test 123")` succeeds in 15 ms but is `VK_PACKET` injection (hook sees `VcUndefined` raw 0xE7, no `KeyTyped`). Per-key simulation: 15 keys in 246 ms, hook sees proper `KeyTyped`. **TypeText step needs both strategies with a per-step switch**: Unicode entry by default, per-key for apps that read scan codes (game consoles). Joel's FF7 console case decides the default for games.
- **`IsEventSimulated` is true for input injected by any process**, not only ours. The engine's guard therefore also ignores other utilities' synthetic input (seen: a volume tool's VolumeUp/Down bursts). Acceptable; document in Engine README.
- With two low-level hooks installed, the later-installed hook runs first and can suppress events before the earlier one sees them. While SP.net runs, Augram installed later wins the race on the shared button; relevant to A11 only.

## B3 hook resilience — mechanism VERIFIED, sleep/lock pending

75 s run: `HookEnabled` fired, first event 3.2 s after install, per-minute counts reported, watchdog idle, clean exit. The watchdog rule implemented: no hook events for 15 s while `GetCursorPos` shows movement → log `HOOK DEAD`, dispose and reinstall. Session-switch and power events are subscribed and logged. Needs hours through sleep, lock and unlock, and a display change.

## Tooling notes

- `<SupportedOSPlatform>` is not an MSBuild property; use the assembly attribute to satisfy CA1416.
- `dotnet format` crashes while a project has compile errors; build first.
- A process launched from a background shell does not take foreground; typing tests must target a window Joel focused. During the self-test the text went to the foreground app at the time: Joel's text editor, where it arrived intact (Joel confirmed 2026-10-05). So `SimulateTextEntry` is verified against a real Win32 editor; the game-console case is still open.
