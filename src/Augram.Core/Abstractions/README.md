# Core/Abstractions

The ports (ADR-0002 §2): the interfaces in the table below, each with the records and enums of its answers and, where a caller may have no implementation, a `Null…` default. Small interfaces, implemented by Engine, Platform.*, Sync.Git and App. Core owns the contract; it never sees an implementation. ADR-0002's `IOverlay` is `IStrokeTrail` here; `IConfigStore` is not a port of this folder: it lives in `Config/`, beside the config it stores, because only Core implements it. A few pure helpers sit beside the port they serve (last table). `HostPlatform`, `KeyCode` and `KeyModifiers` are the vocabulary the rest of Augram shares.

## Ports

| Port | Members | Implemented by | Notes |
|---|---|---|---|
| `IEventLog` | `IsEnabled(level)`, `Log(event)` | Engine `ChannelEventLog`; `NullEventLog` in Core for tests | N4. `Log` must never block the caller. Use the extension methods in `Diagnostics/EventLogExtensions` rather than building a `LogEvent` by hand; they skip the allocation when the level is off. |
| `IHealthSource` | `Current()` | Core `HealthRegistry` | N4 health summary. Read on Diagnostics tab refresh only. |
| `IClock` | `UtcNow`, `MonotonicMs` | Core `SystemClock`; `FakeClock` in tests | `MonotonicMs` stamps every `CaptureEvent`. |
| `IInputSource` | `IsRunning`, `Start(handler)`, `Stop()`, `HookHealthChanged` | Engine `SharpHookInputSource`; `FakeInputSource` in tests | Delivers `RawInput` (a struct; kinds in `RawInputKind`; modifiers as `KeyModifiers`, the type of the ignore-key setting too) to an `InputHandler` on the source's own thread and applies its bool as the suppress decision. `HookHealth` (`Installed`, `Stopped`, `Lost`) may be raised on the hook thread. |
| `IInputSimulator` | `Click`, `Press(button, x, y)` and `Release(button)` (a held-back press handed back to the app and its release, trigger combinations), `PressRemapButton(button, modifiers, x, y)`, `ReleaseRemapButton(button)` and `DragRemapButton(button, x, y, dx, dy)` (a hold remap's button output, F9: the modifiers pressed around its down only; a swallowed physical move re-posted as a drag of it), `RepostsRemapDrags` (true on macOS, where a posted button moves only with posted drags, learnings 0005; read once when the engine is built), `MoveTo`, `Scroll(direction, notches, x, y)` (the Scroll step: the pointer moves to the point and stays there, then one standard notch per count, `ScrollDirection` `Up`/`Down`/`Left`/`Right`), `KeyPress`, `KeyRelease`, `Hotkey(modifiers, key, rightHand)`, `TypeText`, `TypeTextByKeys` | Engine `SharpHookInputSimulator` | Returns `SimulationResult`. Keys are `KeyCode`, Core's platform-neutral enum (letters, digits, F1–F24, navigation, modifiers left/right, Win/Cmd as Meta, media, browser). `Hotkey` presses the left modifier keys, and the right-hand key (RightAlt, RightControl…) for each modifier in `rightHand` (default none; bits outside `modifiers` ignored), so "RAlt+F9" sends RightAlt. The engine worker injects a press's own mouse input (replayed click, hand-back and its release) and a hold remap's outputs, taps and replayed keys (F9), the command executor runs steps and relays a click trigger's click that fired nothing; never the hook thread, and every injected down gets its up (A19). `AsciiKeyLayout` (here, pure) is the US-layout table `TypeTextByKeys` presses; the Type text step checks a text against it and the SendKeys importer maps a modified character through it. |
| `IStrokeTrail` | `Begin`, `Extend`, `End` | App overlay (`TrailOverlayWindow`, or `NativeTrailOverlay` over an `ITrailSurface`); `NullStrokeTrail` in Core | ADR-0002's `IOverlay`. Called on the engine worker; must return at once. |
| `ITrailSurface` | `Verify`, `Cover(start)`, `Park`, `Show`, `Hide`, `SetStyle`, `SetPoints` | Platform.MacOS `MacTrailPanel`; none on Windows | A platform's own trail window, where the toolkit's cannot do it (macOS: over another app's full-screen Space). The App keeps every rule (verify before covering, park between strokes, watchdog); the surface only obeys. UI thread only; the window is made by the first `Verify`. Capture units (global top-left points on macOS); `Cover` returns the `TrailSurfaceArea` it spans. |
| `ICursorProbe` | `TryGetPosition` | Platform.Windows `Win32CursorProbe`, Platform.MacOS `MacCursorProbe` | For the hook watchdog; optional. |
| `ISystemEvents` | `Occurred` (`SystemEventKind`) | Platform.Windows `Win32SystemEvents`, Platform.MacOS `MacSystemEvents` | Session, power, display, and `ForegroundChanged` (another window or app came to the front: the engine's watch checks focus at once for hold remaps, F9); optional. Raised on the UI thread on both; listeners return at once. |
| `IOverlayWindowStyle` | `Apply(handle)` → `OverlayStyleReport` | Platform.Windows `OverlayWindowStyle`; none on macOS (its trail is `MacTrailPanel`, an `ITrailSurface`); `NullOverlayWindowStyle` default | Applies the click-through / no-activate / tool-window styles the toolkit drops on `Show()` (learnings 0001 B2) and reads them back; the App shows the overlay only when the report says click-through. The handle is opaque to Core. |
| `IStartupRegistration` | `Status`, `Set(bool)` | Platform.Windows `RunKeyStartupRegistration`, Platform.MacOS `MacLoginItemRegistration`; `NullStartupRegistration` for tests and platforms without one | F7 start at login as the OS sees it; `Config.GeneralSettings.StartAtLogin` is the user's choice and the App keeps them in step. `StartupStatus`: `NotRegistered`, `Registered`, `Outdated` (starts something else: another path, no `--hidden`), `DisabledByUser` (Task Manager › Startup apps; removed from macOS Login Items), `NeedsApproval` (macOS). `Set(true)` registers and undoes a switch-off made outside Augram; `Set(false)` removes. Failures are `IOException`, `UnauthorizedAccessException`, `SecurityException` or `StartupRegistrationException` (the OS's own refusal, e.g. an `NSError`); the App logs them. |
| `IWindowOperations` | `Platform`, `Supports(op)`, `Perform(op, window, size?)` | Platform.Windows `Win32WindowOperations`, Platform.MacOS `MacWindowOperations` (close, minimize, maximize/restore so far); `NullWindowOperations` default | M2. `WindowOperation` is the semantic list (close, minimize, maximize/restore, always-on-top, center, set size, snap halves); the adapter maps each to its OS and says which it lacks, so a step is authored once for both platforms. Windows ↔ macOS table in `Steps/WindowOp/README.md`. Called on the command executor thread only. |
| `IDisplayModes` | `Platform`, `CanSwitchHdr`, `Displays()`, `SetMode(display, mode)`, `SetHdr(display, on)` | Platform.Windows `Win32DisplayModes`, Platform.MacOS `MacDisplayModes` (no HDR); `NullDisplayModes` default | The Display steps (learnings 0002). `DisplayInfo` (id, name, `DisplayBounds` in the hook's coordinates, main flag, current `VideoMode`, offered modes, `HdrState`); `VideoMode` = `DisplayResolution` (pixels on Windows, points on macOS) + `RefreshRate` (millihertz; `FromLegacyHertz` is Windows' whole-hertz rule, `IsNear` the 0.2 % twin test); `DisplayTarget` and `DisplayLookup` pick the display under the gesture start or the main one; results are `DisplayChangeResult`. Read fresh per call, from the command executor or the UI thread (step form); changes only from the executor. |
| `IWindowSystem` | `WindowAt(x, y)`, `Foreground()`, `WindowKeyAt(x, y)`, `ForegroundKey()`, `Activate(target)` | Platform.Windows `Win32WindowSystem`, Platform.MacOS `MacWindowSystem`; `NullWindowSystem` default | `WindowIdentity` is what F5 matches on. `WindowAt`/`Foreground` read the identity (milliseconds; process lookups); the two keys are cheap (microseconds, no process lookup; 0 = none, null = no cheap answer on this platform) so the ignore list's watch can ask them as the pointer moves and read identities only when a key changed (Windows: `WindowFromPoint` / `GetForegroundWindow` handles; macOS: the `CGWindowID` from a window-list copy at most 250 ms old / the frontmost app's pid). `Activate` applies A20. Called from the command executor and the ignore-list watch, never from a hook handler; `WindowAt` and `WindowKeyAt` also from the App's window finder on the UI thread (they ask no other app anything). |
| `HostPlatform` | enum | | Where a step was authored (F8) and which adapter answered. |
| `HostPlatformExtensions` | `DisplayName()`, `Other()` | | The only place "Windows" / "macOS" and "the other platform" are written; every message, label and marker calls them. |
| `RunningPlatform` | `Current` (get, set), `UseThisMachine()`, `Reset()` | | The one answer to "which platform am I on". The operating system's answer until set; the App's `Program.Main` calls `UseThisMachine()` once, a test sets `Current` and calls `Reset()` in a `finally` (in a collection that never runs in parallel, as `Augram.Core.Tests/Platforms/RunningPlatformTests` does: it is process-wide). `NullWindowOperations`, `NullDisplayModes`, the Open app step and the App read it; `HotkeyText.Names` reads it once set and Windows names until then, so Core tests read the same on every machine. The Engine reads `EnginePorts.Platform` (Engine README). Not for toolkit or library quirks (window chrome, SharpHook): those ask `OperatingSystem` where they are. |
| `IProcessLauncher` | `Launch(ProcessLaunch)` → `ProcessLaunchResult` (`Started`, `Failed`, `Cancelled`, `NotSupported`, with a reason) | Platform.Windows `Win32ProcessLauncher` (shell execute, `runas`, hidden), Platform.MacOS `MacProcessLauncher` (`open`, or the executable); `NullProcessLauncher` default | M2, the Run step. `ProcessLaunch` is file, arguments, working directory, elevated, hidden; `ProcessLaunch.SchemeOf` says when the file is a URI. Never waits for the program to exit; answers within a bounded time (an adapter waiting on a UAC prompt answers `Started` with a note and logs the late outcome). Reasons name the file, never the arguments. Called on the command executor thread only. Adapter table in `Steps/Run/README.md`. |
| `IAppActivator` | `BringToFront(executable)` → `AppActivation` (`AppActivationOutcome`: `Activated`, `NotRunning`, `Failed` with a reason) | Platform.Windows `Win32AppActivator` (its topmost window by executable file name, restored when minimized); `NullAppActivator` on macOS and in tests ("not running": `open -a` brings a running app forward by itself) | The Open app step. Called on the command executor thread only; never throws for an expected failure. |
| `IAppWindow` | `Open()` | App `MainWindowOpener` (posts to the UI thread, returns at once); `NullAppWindow` default (false: no window) | The Open app step's "This app (Augram)": opens and focuses Augram's window as a double click on the tray or menu-bar icon does. |
| `ISyncRepository` | `Folder`, `Prepare(url)`, `Pull()`, `ReadMachineFiles()`, `Publish(machineId, content, message)` → `SyncOperationResult` (`Ok`, `Failed(error)`) | `Augram.Sync.Git` `GitSyncRepository` over the installed git | F8 sync (`../Sync/README.md`): a local clone of a private repo with one file per machine under `machines/`; authentication is git's credential helper, never Augram's. Every member may block for seconds and is called from the sync worker only; none throws for an expected failure (offline, not signed in, a rejected push is pulled and retried once, never force-pushed). |
| `IClipboard` | `Clear()` → `ClipboardResult` (`Succeeded`, `Reason`; `IsSupported` false for "no clipboard here", which the step skips on) | Platform.Windows `Win32Clipboard` (`OpenClipboard`/`EmptyClipboard`/`CloseClipboard`, retried while another app holds it), Platform.MacOS `MacClipboard` (`NSPasteboard clearContents`); `NullClipboard` default | The Clear clipboard step. Called on the command executor thread only, needs no UI thread, bounded (≈ 200 ms worst case on Windows). Adapter table in `Steps/ClearClipboard/README.md`. |

## Pure helpers beside their port

| Helper | What | Used by |
|---|---|---|
| `InputSimulation` | `Worst(a, b)` (the later `SimulationResult` member wins: Unsupported over Failed over Success); `WithModifiersHeld(simulator, keys, action)` (the keys down in order, the action, the keys up in reverse, the worst answer; every key goes down and up whatever an earlier injection answered) and its two halves `PressKeys`/`ReleaseKeys`, for a hold that spans two calls (a hold remap's key output). Injection order is behaviour: Blender reads the modifiers at the button's down | `SharpHookInputSimulator` (`Hotkey`, `PressRemapButton`), the engine's `ClickRelay` and hold remap outputs, `MacRemapButtonSimulator` |
| `AsciiKeyLayout` | `TryGetKey(c, out key, out shift)`, `IndexOfUntypeable(text)`: the US-layout table `IInputSimulator.TypeTextByKeys` presses | the simulator, the Type text step's check, the SendKeys importer |
| `DisplayLookup` | `Find(displays, target, x, y)`, `Main(displays)`: the display a Display step acts on (under the gesture start, or the main one) | the Display mode and HDR steps |
| `RefreshRate` | millihertz; `FromHertz`, `FromLegacyHertz` (Windows' whole hertz, 119 → 119.88), `IsNear`, `Text` | `IDisplayModes` adapters, the Display mode step, the importer |
| `ProcessLaunch.SchemeOf(target)` | the URI scheme of a Run target ("https", "ms-settings"), null for a program, path or bare name | the Run step and its conversion, the importer's Run mapping |
| `SystemClock` | `IClock` over the system clock | the App's modules, `EnginePorts`' default |
