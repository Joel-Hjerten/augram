# Augram.App

The Avalonia desktop app: tray, settings workbench, shared components, dev gallery. MVVM with `CommunityToolkit.Mvvm`; views are XAML plus a near-empty code-behind; view models are disposable projections over Core/Engine stores (ADR-0002 §5, §5a). Screens are *declared* as section/field trees and list specs, rendered by generic lookless components whose look comes from a theme (§5b, §5c).

**May reference:** `Augram.Core`, `Augram.Engine`, `Augram.Platform.Windows`, `Augram.Platform.MacOS`, `Augram.Import.StrokesPlus`, `Augram.Sync.Git` (only `Hosting/SyncModule` names it), and the Avalonia / CommunityToolkit.Mvvm / Microsoft.Extensions.DependencyInjection packages. `CompositionRoot.cs` is the one place services are registered; nothing else calls `new` on a service.

**Must never contain:** business rules, application state that outlives a window (stores and the engine own it; `AppState` only projects two settings for the tray), P/Invoke, or SharpHook.

## Rules of the road

- **Theme rule.** A component never names a colour, font, margin or icon. It uses `{StaticResource Token}` inside its ControlTheme in `Themes/<Theme>/`, or a class (`field-editor`, `help`, `section-title`, `toolbar`, `cell`, ...) that the theme styles. `tests/Augram.App.Tests/Architecture/ComponentColorTests` fails the build on a literal colour under `Components/`.
- **Gallery rule.** A component is not done until `DevGallery/GalleryNavigation` shows it in its states with fake data. Same change, same review.
- **Row rule.** Every list row looks the same everywhere (Joel, 2026-10-07). A row component's template wraps itself in `Border Classes="row"` with its content line in `Grid Classes="row-line"` (`row-line indented` for a command under its section) and sets no padding, margin, height or frame of its own; controls inside a row use the row classes (`expander`, `row-active`, `row-glyph`, `trigger-badge`). The metrics are the `Row.*` tokens (`Row.Padding`, `Row.IndentedPadding`, `Row.ControlSize`, `Row.GlyphSize`); item-list cells use `Row.Padding` and `Grid.list-row` the same minimum height. `tests/Augram.App.Tests/Architecture/RowMetricsTests` fails the build when a `*Row` template sets its own spacing.
- **Declaration rule.** Screens never hand-lay XAML. If a screen needs something the vocabulary lacks, add a field kind or a `CustomField`, not a one-off view.
- **State rule.** View models forward intents to stores and services; they hold UI-only state (selected tab, filter choice). Deleting a view model loses nothing.

## How to add…

**A field kind.** (1) `Declarations/XField.cs`: a sealed record deriving from `Field` with `Kind => "X"`, a `IValueBinding<T>` and the `[CallerFilePath]`/`[CallerLineNumber]` parameters. (2) `Components/Fields/X/XFieldRenderer.cs`: `IFieldRenderer` with `Kind => "X"` that builds the editor and keeps it in step with the binding through `BindingObserver.Attach`. It is found by assembly scan; nothing else is edited. (3) If the editor is a new templated control, give it a ControlTheme in `Themes/Wireframe/Wireframe.axaml`. (4) Add it to the gallery's SectionForm page. `FieldKindCoverageTests` checks the `XField` → `"X"` convention.

**A component.** `Components/<Name>/<Name>.cs` deriving from `TemplatedControl` (properties in, events out, named `PART_*` parts), a `ControlTheme` keyed `{x:Type ns:Name}` in each theme file, a gallery page, and `Region.Mark` on anything the inspector should name.

**A step type's form.** `Components/Steps/<Name>/<Name>StepForm.cs`: an `IStepForm` with `TypeKey => <Name>StepType.Instance.Key` whose `Build(current, changed)` returns a `SectionForm` over a declared `FormScreen`; every binding setter builds the new step record and calls `changed`. It is found by assembly scan (`StepFormRegistry`), so nothing else is edited; `StepFormRegistryTests` fails while a built-in type has no form. Add it to the gallery's StepForms page.

**A screen.** `Screens/<Name>Screen.cs` with `Declare(viewModel)` returning a `FormScreen`, `ListScreen`, `TextScreen` or `ComponentScreen` (one shared component filling the tab, bound to the view model in `Declare`; the Gestures grid). A new screen *shape* needs an `IScreenRenderer` under `Components/ScreenHost/` (also found by scan).

**A tab or sub-tab.** One `NavEntry` in `Navigation/AppNavigation.cs` pointing at the screen's `Declare`. Keys are unique across levels; `Shell.SelectedKey` can select any of them.

**A theme.** Copy `Themes/Wireframe/` to `Themes/<Name>/<Name>.axaml`, override tokens and ControlThemes, add the name to `ThemeSelector.Names`, and set `ThemeSelector.Active`.

## Tray and single instance (F7, A10)

Avalonia's `TrayIcon` raises only `Clicked`, so single versus double click is reconstructed by `ClickDiscriminator` with a 250 ms `DispatcherTimer`: a single click toggles `AppState.Enabled` 250 ms after the click; a second click inside the window opens the main window instead. The menu has Open · Enabled (checkable) · Start at login (checkable) · Sync now (only while a sync repository is set; `SyncTrayItem`) · Quit, and the tooltip ends with the last sync ("Augram (enabled) · synced 14:32"). `SingleInstanceGuard` owns a named mutex and listens on a named pipe; a second launch signals it and exits. Diagnostics: `CompositionRoot` wires `ChannelEventLog` → `InMemorySink` (Diagnostics › Log) + `RollingFileSink` (`<config>/logs`), `HealthRegistry` (Diagnostics › Health, refreshed every second) and `RecognitionLog` (Diagnostics › Recognition); the engine host registers there in step 4b.

## EngineModule (the engine slice of the composition root)

`CompositionRoot.Build` calls `EngineModule.Register(services, …)` after the diagnostics services; `App.StartDesktop` calls `EngineModule.Start(services)` once the main window exists. `Register` adds, in order: `IClock`; `ConfigSession` over a `FileConfigStore` at `AppPaths.ConfigFolder` (load notices go to the log as source `config`; a first run writes the defaults and starter gestures at once; saves are debounced by `TimerSaveScheduler`, a `System.Threading.Timer` whose callback is marshalled to the UI thread so the session stays single-writer); `SettingsStore` and `GestureLibrary` from the session; the input source (`SharpHookInputSource`, or the factory in `EngineModuleOptions.InputSource`, which tests set to a fake so no hook is installed) and `SharpHookInputSimulator`; the Platform adapters (`Win32CursorProbe`, `Win32SystemEvents`, `OverlayWindowStyle`, `RunKeyStartupRegistration`; `PlatformAdapters = false` swaps in the null objects); `TrailOverlayWindow` as `IStrokeTrail`; `EngineHost` with gestures = `GestureLibrary.All`, recognition options = `Settings.Current.Recognition`, and the initial stroke button, thresholds, ignore key and enabled flag read from the store; `EngineSettingsLink`; `StrokeButtonDetection`. `Start` returns after one log line when `EngineKillSwitch` is set (`--no-engine` or `AUGRAM_NO_ENGINE=1`); otherwise it resolves the host (which constructs the overlay on the UI thread, hidden), subscribes the link, syncs start-at-login with the OS, and starts the hook. The headless test app builder only calls `Build`, never `Start`. Disposal runs in reverse through the service provider: the host stops the hook, the session flushes a pending save, the log drains last.

## How settings flow

`SettingsStore` is the only mutable owner of `Settings` (ADR-0002 §5a). Writers: `AppSettingsViewModel` setters (one store change each; the Options page has no Undo / Redo row since 2026-10-07), `AppState.Enabled` / `StartAtLogin` (tray and Options), and `StrokeButtonDetection` (F1 detect-to-assign: `EngineHost.CaptureNextButtonPress`, 5 s timeout). Readers: `EngineSettingsLink` pushes the stroke button, ignore key, thresholds and enabled flag into `EngineHost` on every `Changed` (undo included); the recognizer reads `Recognition` through a delegate per stroke; the overlay reads `Trail` at every `Begin`; `AppState` applies `StartAtLogin` to `IStartupRegistration` and raises `PropertyChanged` for the tray. The view model raises `PropertyChanged` with an empty name on every store change, so every `DelegateBinding` on the page refreshes at once. The config folder is read-only on the page; `--config-folder <path>` (or `=path`) changes it (A17 minimal).

## Why the overlay is a Window, not a component

`Overlay/TrailOverlayWindow` is the one piece of UI with no declaration, theme or gallery entry. It is a top-level: it must cover every monitor, sit above every app, never take focus and never take a click, which are window properties (`Topmost`, `ShowActivated = false`, `IsHitTestVisible = false`, the Win32 extended styles re-applied through `IOverlayWindowStyle` after `Show()`, learnings 0001 B2). Its colour, width and opacity are user settings (F6), not theme tokens, so the theme rule does not apply. It is **hidden whenever no stroke is in progress** (decision 2026-10-06, after a shown-and-empty instance that was not click-through blocked the mouse): a stroke's first frame applies the native styles, shows the window, re-applies and reads them back (`IOverlayWindowStyle` returns an `OverlayStyleReport`; `OverlayStylePolicy` says show or hide); the last frame hides it. If the OS reports the window as not click-through it is hidden at once, an `overlay` Error is logged and the trail is a no-op for the rest of the run; a 1 s watchdog hides a window still visible 3 s after its stroke ended. The 3–11 ms first-segment cost of showing per stroke is accepted; the damage of a wrong style is bounded to one stroke. `EngineModule.Start` creates the window but never shows it, and skips the engine entirely under `--no-engine` / `AUGRAM_NO_ENGINE=1` (`EngineKillSwitch`). Trail calls arrive on the engine worker and go through `TrailBuffer`: append under a lock, post at most one `Dispatcher.UIThread.Post` until the UI thread has taken the frame. Pen width = `Trail.WidthPx` × the scaling of the screen under the stroke start (÷ the window's own scaling, since the window spans monitors). The first rendered segment is timed from `Begin` via `RequestAnimationFrame`, logged as `overlay` / `Trail first frame` and contributed to health as `OverlayFirstFrameMs`.

## Gestures tab (F3, F4, F5a, A7; plan 0001 M1 step 7)

`GesturesModule.Register(services)` is the tab's slice of the composition root (training session, presenters, `GesturesViewModel`); `GesturesModule.NavEntry(services)` is its tab entry. It expects `GestureLibrary`, `SettingsStore` and `IEventLog` to be registered and falls back to the starter set and default recognition options when they are not (tests, gallery).

- **GestureGlyph** draws a gesture's first sample: `GlyphGeometry.Normalise` fits the bounding box into the tile on the longer axis (aspect ratio kept, centred inside `Padding`), the polyline gets round caps and an arrowhead on the last segment; `:inactive` greys it through the theme. The geometry is rebuilt only when the points or the size change.
- **GestureGrid** is presentational: `Tiles` (sorted by the view model, each carrying its A7 duplicates), `CanUndo`/`CanRedo`, `Message` in; one `ActionRequested` event out carrying a `GestureGridAction` (New, Redraw, Rename, Delete, KeepThis, Import, Undo, Redo), the selected tile and, for Rename, the new name. Toolbar buttons (Add new gesture…, Import from StrokesPlus.net…, Undo, Redo), the right-click menu (New, Redraw, Rename, Delete and, on a tile with duplicates, "Keep this, delete its duplicates"), the keymap (`GestureGridKeymap`: F2 on Windows / Return on macOS to rename, Ctrl/Cmd+N, Delete, Ctrl/Cmd+Z, Ctrl+Y / Cmd+Shift+Z) and double-click (Redraw) all end in that event. Rename edits in place inside `GestureTile`; the list's key bindings stand down while an editor has focus. Delete asks nothing; Undo brings it back (A9). Active is per command, not per gesture (F3, 2026-10-07), so a tile has no toggle; a gesture no command uses is drawn greyed in M2.
- **GesturesViewModel** turns actions into `GestureLibrary` calls and shows the rule message (`GestureValidationException`) when one is rejected. Duplicates (A7) come from `Core.Recognition.ConfusionCheck` at `DuplicateCutOff` (90), recomputed 200 ms after the last library change: a tile with duplicates is outlined in red, selecting it lights its partners up with the score (the frame only changes colour, never thickness, so the grid never shifts), and "Keep this, delete its duplicates" removes them in one undo step. There is no diagnostic text line under the grid.

## Training (F3, A6)

`TrainingSession` owns the state: `Begin(TrainingRequest)` (a new gesture, prefilled "New gesture N", or a redraw of an existing one), one stroke that each `ReplaceStroke` replaces (no averaging), the live best match from `GestureMatcher.Rank` against the active library, `Accept()` (adds the gesture, or replaces the redrawn gesture's samples with the stroke, through the library's rules; the exception message is shown inline) and `Cancel()`. The Commands tab's gesture picker opens the same session for New Gesture… and selects what it stored. `TrainingPresenter` shows it as `TrainingWindow` (owned by the main window, centred, Cancel and Accept; Escape cancels, closing the window cancels). `GestureDrawArea` accepts left-button strokes and publishes its `ScreenArea` (physical screen pixels plus render scaling) whenever it moves; `TrainingSession.PublishCanvas` keeps the latest.

Stroke-button routing: the hook suppresses the stroke button, so the window never sees it. The engine wiring calls `ITrainingSession.TryConsume(points, startX, startY)` (or the `TrainingRouting.TryConsume(EngineEvent)` extension) for every completed stroke; when a session is open and the start point is inside the canvas, the points are converted to canvas coordinates, the stroke replaces the current one on the UI thread, and the call returns true. Safe from the engine worker thread. In M1 the engine still ranks and logs the stroke first; that is accepted.

## Commands tab (F5a, F5, F3 picker, F8 markers; plan 0001 M2; Global / Apps split, Joel 2026-10-07)

The tab has two sub-tabs, **Global** (`commands.global`) and **Apps** (`commands.apps`), as StrokesPlus.net keeps Global actions and app actions apart. Both are `CommandsScreen` (one `CommandsWorkbench` filling the sub-tab) over their own `CommandsViewModel`, constructed with a `CommandsScope`; the logic is one class, and the scope only decides the sections (`CommandSections`) and the words. **Apps** has one section per app group (Global left out), and in a group that has categories (Photoshop) each command row carries its category as a small tag; no sub-headers. **Global** has one section per category of the Global group, by name, after an **Uncategorized** section that is there only while some Global command has no category; Uncategorized is never renamed or deleted, a category has no active toggle and no app definition.

`CommandsModule.Register(services)` is the tab's slice of the composition root (the gesture picker and form dialog presenters, `TabNavigator`, the shared `CommandClipboard`, the two view models as keyed singletons by `CommandsScope`, `ICommandLocator`); `CommandsModule.NavEntry(services)` is the tab entry with its two sub-entries. It expects `MappingStore`, `GestureLibrary`, the training session and the `IConfirmPresenter` to be registered and falls back to an empty mapping, the starter set and presenters of its own when they are not (tests, gallery). Register it after `GesturesModule`; without it each sub-tab says so instead of failing the window.

- **CommandsWorkbench** is a sub-tab's layout: `CommandTree` beside `CommandHeader` + `StepList`, the message line below. Properties pass down (including the tree's `TreeHeading`, `NewSectionLabel` and `TreeHelp`, which the screen sets from the view model), intents come up unchanged (`TreeActionRequested`, `StepActionRequested`); where the step panel sits is the template's choice (ADR-0002 §5b).
- **CommandTree** is presentational and never asks which sub-tab it is on: `Sections` (`SectionItem`: a `SectionId` = group id + optional category id, name, active, expanded, all its `CommandItem`s, and what its header offers: `CanRename`, `CanDelete`, `CanEditDefinition`, `CanToggleActive`, the count text), `SelectedSectionId`/`SelectedCommandId`, `Heading`, `NewSectionLabel`, `HelpText` in; one `ActionRequested` out carrying a `CommandTreeAction` (Select, ToggleExpanded, NewSection, NewCommand, Rename, Delete, ToggleActive, Copy, Paste, SetTriggerKind, SetCategory, PickGesture, Undo, Redo), the section and, when one is selected, the command. One flat list (`CommandTreeRows`) of `SectionRow`s (expander, name, count, the active toggle only when the item allows it; a click anywhere on the header selects and toggles it, except on the active box or the name editor; `:collapsed`, and `:pinned` for a section that can be neither renamed nor deleted) and `CommandRow`s (glyph or trigger badge, name, category tag, step summary, F8 marker, active), both on `ItemRow` (the shared active toggle and in-place rename; a row asked to rename before it has a template starts its editor when it gets one). The toolbar (the host's new-section label: "New group" or "New category", no ellipsis since 2026-10-07; New command; the platform filter toggle when the host gives it a label; no Undo/Redo buttons since 2026-10-07, deletes ask first and the keys still undo), the right-click menu and `CommandsKeymap.Current` (Ctrl/Cmd+N, C, V, D, Delete, F2 or Enter on Windows / Return on macOS, a double click on a row, Ctrl/Cmd+Z, Ctrl+Y / Cmd+Shift+Z) end in that event, filtered by what the selected section allows (`CommandTreeMenu.Allows`); key bindings stand down while a name is being edited.
- **CommandHeader** shows the selected command's name, a trigger-kind dropdown (No trigger / Gesture / Wheel up / Wheel down), for a gesture the glyph button, and a **Category** dropdown when the item offers categories (`CommandItem.Categories`: always on Global, with Uncategorized as the empty choice; on Apps only for a group that has categories). Choosing Gesture or clicking the glyph asks the host for the Select Gesture picker; choosing a category raises SetCategory. Both dropdowns are `AskingDropdown`s: put back to the command's real value after every request, so a cancelled picker or a refused change leaves them honest.
- **StepList**: `Steps` (`StepItem`: position, summary, type name, active, the F8 marker from `StepPlatformMarker`: "Windows" when the type is not platform-neutral, "has macOS override" when it carries one), `SelectedIndex`, `StepTypes`, `HasCommand` in; `ActionRequested` out carrying a `StepListAction` (Select, Add, Edit, Duplicate, Copy, Paste, Delete, ToggleActive, Reorder, Undo, Redo). The selected `StepRow` expands in place with its type's form from `StepFormRegistry` (accordion). Rows are reused when the count is unchanged, and the form is kept when the step the store echoes back equals what the form last emitted (typing never loses focus) and rebuilt otherwise (undo). "New step…" opens `StepTypePicker` in a flyout (categories in `StepCategory` order, `Other` never offered, no type key named anywhere); `StepDragReorder` turns a left drag past 6 px into Reorder(from, to) with `:dragging` / `:drop-target` on the rows; the keymap stands down while the expanded form has focus.
- **Step forms** (`Components/Steps/<Name>/`, see "How to add"): Window (operation dropdown labelled by the summaries; width and height only for Set size, starting at 1280×720), Delay (milliseconds), Media key (dropdown), Hotkey (capture field, Ctrl/Alt/Shift/Win toggles each with an "R" right-hand toggle, key dropdown), Imported (read-only: method, description, parameters as "name: value" lines, and the "not supported yet" sentence).
- **Hotkey capture (F5).** `Components/HotkeyCapture/HotkeyCaptureBox` shows the combination ("Ctrl+Shift+T" or "No key set"). Capture, or a click on the field, arms `IKeyCapture`, so every key press goes to the field and none to the OS (Win+L, Alt+Tab, Esc and PrintScreen included); the field shows what is held live and the latest combination wins. Commit is mouse-only: Accept, a pointer press anywhere outside the field, or the window losing activation keep the latest combination and raise `Committed`; Clear commits no key. Every exit gives the keyboard back first; unloading keeps nothing. When the engine ends the capture itself (10 s idle watchdog, hook reset, stop) the field keeps what was pressed and says why. `EngineKeyCapture` wraps `EngineHost.CaptureKeys` and marshals to the UI thread; `EngineModule.Start` publishes it as the application resource `HotkeyCaptureBox.KeyCaptureResourceKey` because step forms are built by scan without services. Under `--no-engine` nothing is published and the field reads its own window's key events (`CaptureWindowWatch`, `AvaloniaKeyMap`) and says Win+L, Alt+Tab and PrintScreen cannot be recorded that way. `HotkeyRecorder` holds the pure "modifier set + one key" logic. **Right-hand modifiers are kept** (F5, Joel 2026-10-07): the recorder remembers which physical modifier keys are held, and one held on the right only becomes `RightHand` ("RAlt+F9", "RCtrl+RShift+P"); held on both sides, or known only from the event's reported mask (held since before the capture), it is plain. The field's `RightHand` property and `HotkeyCommittedEventArgs.RightHand` carry it; Clear resets it. On an AltGr layout (Joel's Swedish one) Windows reports AltGr as a synthesised LeftControl plus RightAlt, so pressing AltGr+F9 records "Ctrl+RAlt+F9"; that is accepted, since replaying it sends what Windows saw. In the form's hand editor each modifier is a `ModifierToggle` (`Components/HotkeyCapture/`): its check box plus a small "R" toggle (tooltip "Right-hand key"), enabled only while the modifier is on; any change emits the normalised step (`HotkeyStep.Normalized()`), so turning a modifier off drops its right-hand bit. The theme of the field and the toggle is `Themes/Wireframe/Hotkey.axaml`, merged by `Wireframe.axaml`.
- **GesturePicker** (F3 "Select Gesture"): every gesture as a `GestureTile` (the tile, not the grid, so no toolbar), single selection, No Gesture / New Gesture… / Cancel / OK (double-click picks). `GesturePickerPresenter` shows it in `GesturePickerWindow` owned by the main window, keeps the tiles in step with the library and, on New Gesture…, opens the shared training popup and selects the gesture the library gained when that session ends Accepted. The view model asks through `IGesturePickerPresenter`.
- **FormDialog** is the small popup form (F7: dialog chrome once): an optional message line, a declared `FormScreen` rendered by `SectionForm`, Confirm (labelled per request) and Cancel. `FormDialogPresenter` shows a `FormDialogRequest` modally in `FormDialogWindow`. The view model uses it for the app group form, `GroupEditViewModel.Declare()`: name, active, suppress globals; executable names as comma-separated text, window title with its regex toggle. The matcher fields the form does not edit (path, class chain, full-screen rule) are kept. Yes/no questions ("Delete group 'Chrome' and its 2 commands?", "Delete command 'X'?", "Delete category 'Media'? Its 3 commands move to Uncategorized.") go through the shared `IConfirmPresenter` (`UsedBy/ConfirmDialog`), the same one the Gestures tab's delete warning uses.

## Sync between machines (F8 sync, Joel 2026-10-07)

The merge, the base state and the run are Core's (`../Augram.Core/Sync/README.md`), the git side is `Augram.Sync.Git`; this is the App's part: when a run happens, on which thread, and what the user sees.

**SyncModule** (`Hosting/`). `CompositionRoot.Build` calls `SyncModule.Register(services, options)` after the engine and tab slices; `App.StartDesktop` calls `SyncModule.Start(services)` right after `EngineModule.Start`, also under `--no-engine` (sync never touches input). `Register` adds `SyncFolders` (`<config>/sync`), `GitSyncRepository` on `<config>/sync/repo` as `ISyncRepository` (machine label = this machine's sync name), `SyncBaseStore` on the config folder (unreadable state files logged as `sync` warnings), `SyncStoreThread`, `SyncCoordinator` over the config session's stores with `SyncStoreThread.Run` as its `onStoreThread`, `SyncService`, the two presenters, `SyncPrompter`, `SyncViewModel` and `SyncHealthContributor`. `SyncModuleOptions` lets tests swap the repository (a fake, no git), the store thread (`(f, _) => f()`), the timers and the UI marshal. `Start` resolves the prompter and the health row, logs "Sync ready" (host only) and starts the service. The headless test app only builds; nothing runs while no repository is set.

**SyncService** (the worker). One dedicated background thread ("Augram sync"), so never two runs at once; requests made while a run is going or queued coalesce into one more run (the user's reason wins for `LastTrigger`). Triggers (`SyncTrigger`):

| Trigger | When | Runs while |
|---|---|---|
| `Start` | once, from `Start()` | repository set, automatic sync on, not paused |
| `LocalChange` | `ChangeDelay` (20 s) after the last `GestureLibrary`/`MappingStore` change the sync did not make, or a new machine name; each change restarts the delay; a run cancels a pending one (it includes the change) | same |
| `Poll` | `PollInterval` (5 min) after the end of every run | same |
| `AutoSyncOn` | automatic sync switched on | same |
| `Manual` | Sync now (Options, tray) | repository set |
| `RepositoryChanged` | the URL set, changed or cleared | always (the user just asked for it; a blank URL runs only the reset) |
| `Join`, `Resolve` | the join answer; conflict resolutions (each `Resolve` in order, then a `Run`) | always |

A run that answers `NeedsJoinChoice` **pauses** automatic triggers (`IsPaused`) until a run answers anything else (the join choice, or a new URL). So does `NeedsUpdate` (a newer Augram wrote to the repo, Core README "Format version"): only Sync now, a new URL or a restart runs again, and on the same build each answers `NeedsUpdate` again without writing anything, so sync resumes once the app restarts on a newer build. Its own store changes are told apart through `SyncStoreThread.IsApplying`, true while the coordinator's apply function runs on the store thread, where the stores raise `Changed` synchronously. `Changed` is raised on the worker when a run starts and ends; `LastReport`, `LastTrigger`, `IsRunning`, `IsPaused`, `OtherMachines` (names from the state, for "from Mac") and `PendingConflicts()` (none while sync is off or right after a reset) are safe from any thread. An exception inside a run is logged and reported as `Failed`; the worker keeps serving.

**Threading.** Store mutations happen only on the UI thread: `SyncStoreThread` runs the coordinator's apply function there synchronously (`Dispatcher.UIThread.Invoke`, or directly when already on it), with a cancellation token. **Shutdown:** `Dispose` (through the provider, before the config session flushes) cancels the timers, `Stop`s the store thread (a waiting `Invoke` gives up, a queued one checks the flag on the UI thread and applies nothing) and waits up to 2 s for the worker; a run stuck in git is abandoned on its background thread and can no longer apply or save. Nothing runs after `Dispose`.

**Repository changes** (`SyncFolders`). `sync/repository-url.txt` remembers the URL the clone and the state belong to. Before every run the worker calls `SyncFolders.Prepare(url)`: no marker yet → remember the URL (an existing clone is taken as this URL's); a different URL or none → move `sync/repo` aside to `sync/repo-old-<yyyyMMdd-HHmmss>` (never deleted; the git adapter refuses a clone of another URL), `SyncBaseStore.Clear()`, remember the new URL (or delete the marker), log "Sync state cleared: the repository changed". The next run then asks the join question again. Because the marker is on disk, a URL changed just before quitting is reset at the next start. A clone that cannot be moved (a file open in it) fails the run with that line and nothing changes.

**Options › Sync** (`Screens/OptionsSyncSection`, included last by `OptionsScreen` when a `SyncViewModel` is registered). Repository (a private GitHub repo; the help line says sign-in is git's own and Augram stores no password), This machine, Automatic sync, Status (Sync now + the status line), Conflicts ("2 conflicts with Mac" + Resolve…, shown only while some are pending, through `Field.Visible`), Details (the last run's repairs and notes, shown only when there are some). The two text fields are drafts while typed: every keystroke re-checks (`SyncSettingsRules.UrlProblem`, a blank name) and shows the problem under the box in `TextBlock.error`; leaving the box (or a click elsewhere, `ClickAwayFocus`) or Enter commits a valid draft as one `SettingsStore.SetSync`, Escape reverts. So a URL is never applied half-typed (each new URL resets the state). A stored value changed elsewhere replaces the draft; one being typed survives unrelated settings changes. Status lines: "Off: paste a repository address above…", "Syncing…", "Paused: choose how to join (Sync now asks again).", "Paused: Mac uses a newer Augram. Update this machine (pull, rebuild, restart) to resume.", "Not synced yet.", "Up to date (last synced 14:32).", "Last synced 14:32: 3 commands changed from Mac.", "Sync failed at 14:32: <error line>".

**Join dialog.** `SyncPrompter` listens to the service and, when a finished run's report is `NeedsJoinChoice` (once per report, one dialog at a time), asks `ISyncJoinPresenter` on the UI thread; the answer runs `SyncService.Join`, Cancel leaves sync paused. `SyncJoinPresenter` shows `SyncJoinViewModel.Declare()` in the shared `FormDialog` (680 px wide), modal to the main window when it is open, otherwise as a window of its own (the start-up run usually finds Augram in the tray). The form: the machines already in the repo, newest first ("PC-HOME: Last written 7 Oct 07:40 · 105 gestures · 9 groups · 212 commands"); "Join by" with **Use the synced settings on this machine (recommended)** (default) and **Merge with this machine's settings**; a "What happens" line for the selected one (replaced by the newest machine's, previous file kept as a backup / both kept, items imported separately on each machine appear twice). Confirm is "Join".

**Conflict dialog.** Resolve… calls `ISyncConflictPresenter.ResolveAsync(pending)`; Apply returns every conflict with its choice and `SyncService.Resolve` runs them on the worker, then syncs. `SyncConflictPresenter` builds a `SyncConflictsViewModel` against the stores (names for the summaries) and shows `SyncConflictWindow`: the summary line, a help line, the `SyncConflictList` component and Cancel / Apply. One `SyncConflictRow` per conflict (row rule: `Border.row` + `Grid.row-line`): name and "Gesture · with Mac", this machine's and the other machine's version side by side (a gesture as two `GestureGlyph.row-glyph`, anything else as a one-line summary or "deleted"), and a choice dropdown, Keep mine by default. Keep both is offered only for a gesture or a command present on both machines (`SyncConflictsViewModel.Allowed`). Columns: `SyncConflict.ItemColumn` / `ChoiceColumn` tokens; theme in `Themes/Wireframe/Sync.axaml`.

**Tray and health.** `SyncTrayItem` adds Sync now to the tray menu while a repository is set (disabled during a run) and a short status to the tooltip ("sync paused: Mac uses a newer Augram" for `NeedsUpdate`). `SyncHealthContributor` fills `HealthSnapshot.LastSyncOutcome` / `LastSyncAt`; Diagnostics › Health shows "Last sync: UpToDate at 14:32:05", or "Paused (Mac uses a newer Augram) at 14:32:05".

**First sync, per machine.** Paste the repo's https URL into Options › Sync › Repository and leave the field. The worker clones it into `<config>/sync/repo` (Git Credential Manager's sign-in window on Windows; the Keychain helper or `gh auth setup-git` on macOS, `../Augram.Sync.Git/README.md`). The first machine finds no other file: "Up to date", and its file is pushed. The next machine finds it and asks the join question.
