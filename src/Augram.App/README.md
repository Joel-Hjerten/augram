# Augram.App

The Avalonia desktop app: tray, settings workbench, shared components, dev gallery. MVVM with `CommunityToolkit.Mvvm`; views are XAML plus a near-empty code-behind; view models are disposable projections over Core/Engine stores (ADR-0002 §5, §5a). Screens are *declared* as section/field trees and list specs, rendered by generic lookless components whose look comes from a theme (§5b, §5c).

**May reference:** `Augram.Core`, `Augram.Engine`, `Augram.Platform.Windows`, `Augram.Platform.MacOS`, `Augram.Import.StrokesPlus`, `Augram.Sync.Git` (only `Hosting/SyncModule` names it), and the Avalonia / CommunityToolkit.Mvvm / Microsoft.Extensions.DependencyInjection packages, plus Velopack (only `Program` names it, see "Packaging and releases"). `CompositionRoot.cs` is the one place services are registered; nothing else calls `new` on a service.

**Must never contain:** business rules, application state that outlives a window (stores and the engine own it; `AppState` only projects two settings for the tray), P/Invoke, or SharpHook.

## Rules of the road

- **Theme rule.** A component never names a colour, font, margin or icon. It uses `{StaticResource Token}` inside its ControlTheme in `Themes/<Theme>/`, or a class (`field-editor`, `help`, `section-title`, `toolbar`, `cell`, ...) that the theme styles. `tests/Augram.App.Tests/Architecture/ComponentColorTests` fails the build on a literal colour under `Components/`.
- **Gallery rule.** A component is not done until `DevGallery/GalleryNavigation` shows it in its states with fake data. Same change, same review.
- **Row rule.** Every list row looks the same everywhere (Joel, 2026-10-07). A row component's template wraps itself in `Border Classes="row"` with its content line in `Grid Classes="row-line"` (`row-line indented` for a command under its section) and sets no padding, margin, height or frame of its own; controls inside a row use the row classes (`expander`, `row-active`, `row-glyph`, `trigger-badge`). The metrics are the `Row.*` tokens (`Row.Padding`, `Row.IndentedPadding`, `Row.ControlSize`, `Row.GlyphSize`); item-list cells use `Row.Padding` and `Grid.list-row` the same minimum height. `tests/Augram.App.Tests/Architecture/RowMetricsTests` fails the build when a `*Row` template sets its own spacing.
- **Declaration rule.** Screens never hand-lay XAML. If a screen needs something the vocabulary lacks, add a field kind or a `CustomField`, not a one-off view.
- **State rule.** View models forward intents to stores and services; they hold UI-only state (selected tab, filter choice). Deleting a view model loses nothing.

## How to add…

**A field kind.** (1) `Declarations/XField.cs`: a sealed record deriving from `Field` with `Kind => "X"`, a `IValueBinding<T>` and the `[CallerFilePath]`/`[CallerLineNumber]` parameters. (2) `Components/Fields/X/XFieldRenderer.cs`: `IFieldRenderer` with `Kind => "X"` that builds the editor and keeps it in step with the binding through `BindingObserver.Attach`. It is found by assembly scan; nothing else is edited. (3) If the editor is a new templated control, give it a ControlTheme in `Themes/Wireframe/Wireframe.axaml`. (4) Add it to the gallery's SectionForm page. `FieldKindCoverageTests` checks the `XField` → `"X"` convention.

**A component.** `Components/<Name>/<Name>.cs` deriving from `TemplatedControl` (properties in, events out, named `PART_*` parts), a `ControlTheme` keyed `{x:Type ns:Name}` in each theme file, a gallery page, and `Region.Mark` on anything the inspector should name.

**A step type's form.** `Components/Steps/<Name>/<Name>StepForm.cs`: an `IStepForm` with `TypeKey => <Name>StepType.Instance.Key` whose `Build(current, changed)` returns a `SectionForm` over a declared `FormScreen`; every binding setter builds the new step record and calls `changed`. It is found by assembly scan (`StepFormRegistry`), so nothing else is edited; `StepFormRegistryTests` fails while a built-in type has no form. Add it to the gallery's StepForms page.

**A screen.** `Screens/<Name>Screen.cs` with `Declare(viewModel)` returning a `FormScreen`, `ListScreen`, `TextScreen` or `ComponentScreen` (one shared component filling the tab, bound to the view model in `Declare`; the Gestures grid). A new screen *shape* needs an `IScreenRenderer` under `Components/ScreenHost/` (also found by scan).

**A tab or sub-tab.** One `NavEntry` in `Navigation/AppNavigation.cs` pointing at the screen's `Declare`. Keys are unique across levels; `Shell.SelectedKey` can select any of them.

**A theme.** Copy `Themes/Wireframe/` to `Themes/<Name>/<Name>.axaml`, override tokens and ControlThemes, add the name to `ThemeSelector.Names`, and set `ThemeSelector.Active`.

## Packaging and releases

`Program.Main` begins with `VelopackApp.Build().Run()`: Velopack's Setup, updater and uninstaller start the exe with hook arguments, and that line answers them and exits before the single-instance guard or any UI exists, so it stays first. `node scripts/package.mjs windows|mac` publishes and packs the installer; cutting a release, where the app installs, signing and the macOS Info.plist: [docs/release.md](../../docs/release.md). Nothing checks for updates yet; when something does, it is a `Hosting/` service registered in `CompositionRoot` around Velopack's `UpdateManager` over the GitHub releases (docs/release.md, "Not built yet").

## Tray, version and channel, single instance (F7, A10)

Avalonia's `TrayIcon` raises only `Clicked`, so single versus double click is reconstructed by `ClickDiscriminator` with a 250 ms `DispatcherTimer`: a single click toggles `AppState.Enabled` 250 ms after the click; a second click inside the window opens the main window instead. The menu has Open · Enabled (checkable) · Start at login (checkable; disabled in a Dev build) · Sync now (only while a sync repository is set; `SyncTrayItem`) · Quit, and the tooltip starts with the build's name and ends with the last sync ("Augram (Dev) (enabled) · synced 14:32", `AppTray.ToolTipFor`); while a "disable while focused" ignored app has focus it says "Augram (paused: VMware is focused)" instead of "(enabled)" (`EnginePauseState`, see "Ignored tab"); the icon does not change. Diagnostics: `CompositionRoot` wires `ChannelEventLog` → `InMemorySink` (Diagnostics › Log) + `RollingFileSink` (`<config>/logs`), `HealthRegistry` (Diagnostics › Health, refreshed every second) and `RecognitionLog` (Diagnostics › Recognition); the engine host registers there in step 4b.

**Dock on macOS (Joel, 2026-10-08).** The Dock icon is there only while the main window is open: `Views/MacDockPresence` follows the window's visibility and switches the activation policy (`Platform.MacOS/MacDock`: regular with a Dock icon, accessory without). Closing the window hides it (`MainWindow.OnClosing`, both platforms); on macOS minimizing hides it too, so the window never sits in the Dock without an app icon. Open in the tray menu or a second launch shows both again; Quit is the only way out. The bundle keeps `LSUIElement` unset, so a launch starts with the Dock icon and the window. Windows is unchanged: minimize goes to the taskbar.

**Version and channel (2026-10-08).** The version is one property, `<Version>` in `Directory.Build.props` (0.2.0); the SDK appends `+<commit>` to the informational version from git. The build channel is the MSBuild property `AugramChannel`, `Dev` by default (every local and CI build); the release script passes `-p:AugramChannel=Release`. `Augram.App.csproj` embeds it as `[AssemblyMetadata("AugramChannel", …)]`. `Hosting/AppInfo` reads both (`AppInfo.Current`, registered in `CompositionRoot`): `Version` (0.2.0), `Commit` (the first 7 characters), `InformationalVersion` (0.2.0+3f1c2ab), `Channel`, `IsDev`, `DisplayName` ("Augram (Dev)" or "Augram"); a missing or unknown channel reads as Dev, the safe side. Joel's rule: there is no mistaking which build runs. The main window's title is `DisplayName`, the tray tooltip starts with it, Options › About shows version, commit and channel (read-only notes), and the first log line of a run is `app` / `App started` with version, commit, channel, theme and OS. Dialogs and the training window keep their own titles.

**Start at login is the installed build's.** In the Dev channel `AppState` never calls `IStartupRegistration` (neither writes nor removes, so the installed build's Run entry survives a dev run and logging in never starts a dev copy) and ignores sets of `StartAtLogin`; `CanChangeStartAtLogin` is false, Options shows the toggle disabled with "Start at login applies to the installed Augram; this is a development build.", and the tray item is disabled. At startup it logs `startup` / `Start at login left to the installed Augram`. The Release channel behaves as before.

**One Augram at a time (A10; Joel, 2026-10-08: the installed or a dev build, never both).** Both channels use the same name, `Program.InstanceName`. `Program.Main` calls `InstanceStartup.Begin()` before building anything:

1. `SingleInstanceGuard.TryAcquire` takes the mutex (per user; per logon session on Windows) and starts the pipe listener → `Run`.
2. Taken: it sends Hello with its identity (`InstanceIdentity`: channel, version, commit, executable path) and gets the running one's back.
   - Same channel and same executable (a rebuilt copy at the same path included) → it sends Show (reason "same install"), the running one shows its window, this launch exits (the old behaviour).
   - A different channel or executable → `Choose`: `Program` starts Avalonia, and `App` runs `InstanceStartup.ChooseAsync` before resolving anything else, so no engine, hook, overlay, tray or sync exists in this launch yet. `ITakeOverPresenter` (`Views/TakeOverPresenter`, the shared `ConfirmDialog` shown without an owner) asks "Augram 0.2.0 (installed) is already running. Quit it and start Augram (Dev) instead?" (two dev copies: "…is already running from another folder…" with both paths) with **Quit it and start this one** / **Cancel**. Confirm sends Quit and waits up to 10 s for the mutex; the running one answers, then shuts down as the tray's Quit does (engine stops, config flushes, sync abandons a run on its background thread, `Program` releases the name last), and this launch starts and shows its window. On timeout it says "…did not quit within 10 seconds. Quit it from its tray icon, then start Augram (Dev) again." and exits. Cancel sends Show (reason "take-over cancelled") and exits.
   - An Augram from before identities (0.1) → it was shown by the connection itself; this launch exits.
   - No answer within 2 s (the running one is starting, stopping or stuck) → it waits up to 3 s more for the mutex, then runs or exits.

The pipe protocol (`InstanceProtocol`) stays compatible both ways. A request is the byte 2 and one JSON line (`request`, `reason`, `channel`, `version`, `commit`, `path`); every answer is the listener's identity as one JSON line. The listener treats anything else (0.1's one byte, a connection that closes or breaks before a full request, an unknown verb) as Show: the connection is the request, and a broken pipe on that read must not lose it (a Windows CI run did, 2026-10-07). A 0.1 listener is inbound only, so Windows refuses the two-way connection and `Send` asks it the old way (`SignalExisting`); off Windows it reads one byte and closes, which reads as `Older`. On Windows the pipe is `CurrentUserOnly` both ways (pipe names are machine-wide there), so another user's Augram can never be shown or quit. Off Windows a pipe is a domain socket that lives only while a server stream does, and a client that connects while the previous request is being served waits in the socket's queue: the listener makes the next server stream before it lets go of the served one, or that client is dropped (the Show or Quit after a Hello was lost on macOS, 2026-10-08). The mutex is held by its own parked thread (`NamedMutexOwner`): a mutex belongs to the thread that took it, and the take-over waits for it from the UI thread without blocking. `Dispose` stops the listener first, then releases. Logging: the running side logs `app` / `Another Augram is starting`, `Asked to show the window by another launch` and `Asked to quit by another Augram` with the asker's identity and reason; the launch that takes over logs `Took over from another Augram` (who, and how long it waited) right after `App started`. A launch that exits writes no log of its own, because two processes appending to one daily file would clobber each other's lines; its side is in the running one's lines. Tests use real mutexes and pipes under a unique name per test (`Support/InstanceTesting`) and fake the dialog (`FakeTakeOverPresenter`).

## EngineModule (the engine slice of the composition root)

`CompositionRoot.Build` calls `EngineModule.Register(services, …)` after the diagnostics services; `App.StartDesktop` calls `EngineModule.Start(services)` once the main window exists. `Register` adds, in order: `IClock`; `ConfigSession` over a `FileConfigStore` at `AppPaths.ConfigFolder` (load notices go to the log as source `config`; a first run writes the defaults and starter gestures at once; saves are debounced by `TimerSaveScheduler`, a `System.Threading.Timer` whose callback is marshalled to the UI thread so the session stays single-writer); `SettingsStore` and `GestureLibrary` from the session; the input source (`SharpHookInputSource`, or the factory in `EngineModuleOptions.InputSource`, which tests set to a fake so no hook is installed) and `SharpHookInputSimulator`; the Platform adapters (`Win32CursorProbe`, `Win32SystemEvents`, `OverlayWindowStyle`, `RunKeyStartupRegistration`, the window system and operations, `Win32ProcessLauncher` or `MacProcessLauncher` as `IProcessLauncher` for the Run step, `Win32Clipboard` or `MacClipboard` as `IClipboard` for the Clear clipboard step; `PlatformAdapters = false` swaps in the null objects); `TrailOverlayWindow` as `IStrokeTrail`; `EngineHost` with gestures = `GestureLibrary.All`, recognition options = `Settings.Current.Recognition`, and the initial stroke button, thresholds, ignore key and enabled flag read from the store; `EngineSettingsLink` (settings, and every mapping change as `EngineHost.MappingChanged`, so an Ignored-tab edit reaches the ignore-list watch at once); `EnginePauseState`; `StrokeButtonDetection`. `Start` returns after one log line when `EngineKillSwitch` is set (`--no-engine` or `AUGRAM_NO_ENGINE=1`); otherwise it resolves the host (which constructs the overlay on the UI thread, hidden), subscribes the link, syncs start-at-login with the OS (the installed build only; a Dev build leaves it alone), starts the hook, and links `EnginePauseState` to the host. The headless test app builder only calls `Build`, never `Start`. Disposal runs in reverse through the service provider: the host stops the hook, the session flushes a pending save, the log drains last.

## How settings flow

`SettingsStore` is the only mutable owner of `Settings` (ADR-0002 §5a). Writers: `AppSettingsViewModel` setters (one store change each; the Options page has no Undo / Redo row since 2026-10-07), `AppState.Enabled` / `StartAtLogin` (tray and Options), and `StrokeButtonDetection` (F1 detect-to-assign: `EngineHost.CaptureNextButtonPress`, 5 s timeout). Readers: `EngineSettingsLink` pushes the stroke button, ignore key, thresholds and enabled flag into `EngineHost` on every `Changed` (undo included); the recognizer reads `Recognition` through a delegate per stroke; the overlay reads `Trail` at every `Begin`; `AppState` applies `StartAtLogin` to `IStartupRegistration` (Release channel only) and raises `PropertyChanged` for the tray. The view model raises `PropertyChanged` with an empty name on every store change, so every `DelegateBinding` on the page refreshes at once. The config folder is read-only on the page; `--config-folder <path>` (or `=path`) changes it (A17 minimal).

## Why the overlay is a Window, not a component

`Overlay/TrailOverlayWindow` is the one piece of UI with no declaration, theme or gallery entry. It is a top-level: it must cover every monitor, sit above every app, never take focus and never take a click, which are window properties (`Topmost`, `ShowActivated = false`, `IsHitTestVisible = false`, the Win32 extended styles re-applied through `IOverlayWindowStyle` after `Show()`, learnings 0001 B2). Its colour, width and opacity are user settings (F6), not theme tokens, so the theme rule does not apply. It is **hidden whenever no stroke is in progress** (decision 2026-10-06, after a shown-and-empty instance that was not click-through blocked the mouse): a stroke's first frame applies the native styles, shows the window, re-applies and reads them back (`IOverlayWindowStyle` returns an `OverlayStyleReport`; `OverlayStylePolicy` says show or hide); the last frame hides it. If the OS reports the window as not click-through it is hidden at once, an `overlay` Error is logged and the trail is a no-op for the rest of the run; a 1 s watchdog hides a window still visible 3 s after its stroke ended. The 3–11 ms first-segment cost of showing per stroke is accepted; the damage of a wrong style is bounded to one stroke. `EngineModule.Start` creates the window but never shows it, and skips the engine entirely under `--no-engine` / `AUGRAM_NO_ENGINE=1` (`EngineKillSwitch`). Trail calls arrive on the engine worker and go through `TrailBuffer`: append under a lock, post at most one `Dispatcher.UIThread.Post` until the UI thread has taken the frame. Pen width = `Trail.WidthPx` × the scaling of the screen under the stroke start (÷ the window's own scaling, since the window spans monitors). The first rendered segment is timed from `Begin` via `RequestAnimationFrame`, logged as `overlay` / `Trail first frame` and contributed to health as `OverlayFirstFrameMs`.

## Gestures tab (F3, F4, F5a, A7; plan 0001 M1 step 7)

`GesturesModule.Register(services)` is the tab's slice of the composition root (training session, presenters, `GesturesViewModel`); `GesturesModule.NavEntry(services)` is its tab entry. It expects `GestureLibrary`, `SettingsStore` and `IEventLog` to be registered and falls back to the starter set and default recognition options when they are not (tests, gallery).

- **GestureGlyph** draws a gesture's first sample: `GlyphGeometry.Normalise` fits the bounding box into the tile on the longer axis (aspect ratio kept, centred inside `Padding`), the polyline gets round caps and an arrowhead on the last segment; `:inactive` greys it through the theme. The template draws it with `GlyphStroke`: from a shaded start (`Brush.GlyphStart`) to the end colour (`Brush.Glyph`) by arc length; the running app sets both from Options › Trail › Colour (`Themes/GlyphColourLink`; the start is `GlyphColours.StartFor`: darker, hue-shifted towards blue-violet the shorter way round, so yellow starts amber, cyan blue), inactive pictures stay grey, so where a stroke starts and which way it runs reads along its whole length (Joel, 2026-10-08; pictures only, never the live trail or the draw area). The geometry is rebuilt only when the points or the size change.
- **GestureGrid** is presentational: `Tiles` (sorted by the view model, each carrying its A7 duplicates), `CanUndo`/`CanRedo`, `Message` in; one `ActionRequested` event out carrying a `GestureGridAction` (New, Redraw, Rename, Delete, KeepThis, Import, Undo, Redo), the selected tile and, for Rename, the new name. Toolbar buttons (Add new gesture…, Import from StrokesPlus.net…, Undo, Redo), the right-click menu (New, Redraw, Rename, Delete and, on a tile with duplicates, "Keep this, delete its duplicates"), the keymap (`GestureGridKeymap`: F2 on Windows / Return on macOS to rename, Ctrl/Cmd+N, Delete, Ctrl/Cmd+Z, Ctrl+Y / Cmd+Shift+Z) and double-click (Redraw) all end in that event. Rename edits in place inside `GestureTile`; the list's key bindings stand down while an editor has focus. Delete asks nothing; Undo brings it back (A9). Active is per command, not per gesture (F3, 2026-10-07), so a tile has no toggle; a gesture no command uses is drawn greyed in M2.
- **GesturesViewModel** turns actions into `GestureLibrary` calls and shows the rule message (`GestureValidationException`) when one is rejected. Duplicates (A7) come from `Core.Recognition.ConfusionCheck` at `DuplicateCutOff` (90), recomputed 200 ms after the last library change: a tile with duplicates is outlined in red, selecting it lights its partners up with the score (the frame only changes colour, never thickness, so the grid never shifts), and "Keep this, delete its duplicates" removes them in one undo step. There is no diagnostic text line under the grid.

## Training (F3, A6)

`TrainingSession` owns the state: `Begin(TrainingRequest)` (a new gesture, prefilled "New gesture N", or a redraw of an existing one), one stroke that each `ReplaceStroke` replaces (no averaging), the live best match from `GestureMatcher.Rank` against the active library, `Accept()` (adds the gesture, or replaces the redrawn gesture's samples with the stroke, through the library's rules; the exception message is shown inline) and `Cancel()`. The Commands tab's gesture picker opens the same session for New Gesture… and selects what it stored. `TrainingPresenter` shows it as `TrainingWindow` (owned by the main window, centred, Cancel and Accept; Escape cancels, closing the window cancels). `GestureDrawArea` accepts left-button strokes and publishes its `ScreenArea` (physical screen pixels plus render scaling) whenever it moves; `TrainingSession.PublishCanvas` keeps the latest.

Stroke-button routing: the hook suppresses the stroke button, so the window never sees it. The engine wiring calls `ITrainingSession.TryConsume(points, startX, startY)` (or the `TrainingRouting.TryConsume(EngineEvent)` extension) for every completed stroke; when a session is open and the start point is inside the canvas, the points are converted to canvas coordinates, the stroke replaces the current one on the UI thread, and the call returns true. Safe from the engine worker thread. In M1 the engine still ranks and logs the stroke first; that is accepted.

## Window finder (F5 app identification; SP.net's crosshair; Joel 2026-10-09)

Drag-to-identify on the identification form app groups (Commands › Apps) and ignored apps (Ignored tab) share. Press a magnifier with the left button, drag it onto any window, release: the window under the pointer fills the form. `Components/WindowFinder/WindowFinder` is the magnifier: while dragging the pointer is captured, the cursor is a crosshair, `:finding` is set and a popup above the magnifier says what is under the pointer (`HoverText`: "chrome.exe · Google Chrome", or what a field's finder would take: the path, the title, the classes, or why there is none). Released over another app's window it raises `Picked` with the `WindowIdentity`; over Augram's own windows (settings window, dialogs, the popup itself), over nothing, or after Esc, a right-click or a lost capture it picks nothing, and the release never reaches the window underneath.

- **On the form** (`AppMatcherEditViewModel` + `.Picking`, through `Field.Accessory` and `WindowFinderAccessory`): "Identify window" at the top adds the window's executable to this platform's list (appended, never replacing; skipped when listed in any case) and shows the window's path, title and classes on rows of their own ("Its path", "Its title", "Its classes"; hidden while empty), each with a Use button that copies it into its field. A magnifier also sits before this platform's executables (the other platform's list has none: its windows are not on this screen), the executable path and the window title (each filled exactly, its regex toggle off) and, on Windows, the window classes (the window's class chain: own, parent, root, owner). Every fill sets the form's properties like typing, so the host applies it and its undo takes it back; a fill of two properties (path or title plus its toggle) raises one change, so it is one undo step. A window without the value (a protected process's path, an untitled window, a Mac window's classes) fills nothing. The identified window is UI state (`IdentifiedWindowViewModel`), never an edit; selecting another group or app starts without one.
- **Reading the window.** `WindowProbe` asks `IWindowSystem` on the UI thread (`WindowAt` and `WindowKeyAt` ask no other app anything on either platform): while dragging, the cheap `WindowKeyAt` first and `WindowAt` only when the key changes (at most every 50 ms on a platform without a key); at the release a fresh `WindowAt`. The window system is the application resource `WindowFinder.WindowSystemResourceKey`, published by `EngineModule.Start` before the kill-switch check (reading changes nothing, so it works under `--no-engine`); tests and the gallery may set `WindowSystem` instead.
- **Outside the window and coordinates.** Avalonia's pointer capture is the platform's: on Windows `SetCapture`, so moves and the release keep arriving while the button is held anywhere on screen; on macOS AppKit sends the drag and the mouse-up to the window the press was in. The position comes relative to the magnifier, far outside it, and `PointToScreen` converts it to the window system's units: **physical pixels on Windows** (per-monitor DPI aware: the client position is scaled back by the window's own scaling and offset by `ClientToScreen`, so a window on another monitor at another scale reads right) and **points from the top left of the main display on macOS** (Avalonia.Native flips AppKit's bottom-left screen coordinates; the window server's list uses the same points; `src/Augram.Platform.MacOS/README.md`).
- **No highlight frame** around the hovered window (Spy++ style), on purpose: no port gives a window's bounds, and drawing one needs a second overlay window, which invariant 6 allows only verified click-through, hidden on release and watched; that is a slice of its own with a run on Joel's machine, not something to ship unseen. The popup's text is the feedback.

## Sync between machines (F8 sync, Joel 2026-10-07)

The merge, the base state and the run are Core's (`../Augram.Core/Sync/README.md`), the git side is `Augram.Sync.Git`; this is the App's part: when a run happens, on which thread, and what the user sees.

**SyncModule** (`Hosting/`). `CompositionRoot.Build` calls `SyncModule.Register(services, options)` after the engine and tab slices; `App.StartDesktop` calls `SyncModule.Start(services)` right after `EngineModule.Start`, also under `--no-engine` (sync never touches input). `Register` adds `SyncFolders` (`<config>/sync`), `GitSyncRepository` on `<config>/sync/repo` as `ISyncRepository` (machine label = this machine's sync name), `SyncBaseStore` on the config folder (unreadable state files logged as `sync` warnings), `SyncStoreThread`, `SyncCoordinator` over the config session's stores with `SyncStoreThread.Run` as its `onStoreThread`, `SyncService`, the two presenters, `SyncPrompter`, `SyncViewModel` and `SyncHealthContributor`. `SyncModuleOptions` lets tests swap the repository (a fake, no git), the store thread (`(f, _) => f()`), the timers and the UI marshal. `Start` resolves the prompter and the health row, logs "Sync ready" (host only) and starts the service. The headless test app only builds; nothing runs while no repository is set.

**SyncService** (the worker). One dedicated background thread ("Augram sync"), so never two runs at once; requests made while a run is going or queued coalesce into one more run (the user's reason wins for `LastTrigger`). Triggers (`SyncTrigger`):

| Trigger | When | Runs while |
|---|---|---|
| `Start` | once, from `Start()` | repository set, automatic sync on, not paused |
| `LocalChange` | `ChangeDelay` (20 s) after the last `GestureLibrary`/`MappingStore` change the sync did not make, or a new machine name; each change restarts the delay; a run cancels a pending one (it includes the change) | same |
| `Poll` | `PollInterval` (5 min) after the end of every run | same |
| `AutoSyncOn` | automatic sync switched on | same |
| `Manual` | Sync now (Options, tray) | repository set |
| `RepositoryChanged` | the URL set, changed or cleared | always (the user just asked for it; a blank URL runs only the reset) |
| `Join`, `Resolve` | the join answer; conflict resolutions (each `Resolve` in order, then a `Run`) | always |

A run that answers `NeedsJoinChoice` **pauses** automatic triggers (`IsPaused`) until a run answers anything else (the join choice, or a new URL). So does `NeedsUpdate` (a newer Augram wrote to the repo, Core README "Format version"): only Sync now, a new URL or a restart runs again, and on the same build each answers `NeedsUpdate` again without writing anything, so sync resumes once the app restarts on a newer build. Its own store changes are told apart through `SyncStoreThread.IsApplying`, true while the coordinator's apply function runs on the store thread, where the stores raise `Changed` synchronously. `Changed` is raised on the worker when a run starts and ends; `LastReport`, `LastTrigger`, `IsRunning`, `IsPaused`, `OtherMachines` (names from the state, for "from Mac") and `PendingConflicts()` (none while sync is off or right after a reset) are safe from any thread. An exception inside a run is logged and reported as `Failed`; the worker keeps serving.

**Threading.** Store mutations happen only on the UI thread: `SyncStoreThread` runs the coordinator's apply function there synchronously (`Dispatcher.UIThread.Invoke`, or directly when already on it), with a cancellation token. **Shutdown:** `Dispose` (through the provider, before the config session flushes) cancels the timers, `Stop`s the store thread (a waiting `Invoke` gives up, a queued one checks the flag on the UI thread and applies nothing) and waits up to 2 s for the worker; a run stuck in git is abandoned on its background thread and can no longer apply or save. Nothing runs after `Dispose`.

**Repository changes** (`SyncFolders`). `sync/repository-url.txt` remembers the URL the clone and the state belong to. Before every run the worker calls `SyncFolders.Prepare(url)`: no marker yet → remember the URL (an existing clone is taken as this URL's); a different URL or none → move `sync/repo` aside to `sync/repo-old-<yyyyMMdd-HHmmss>` (never deleted; the git adapter refuses a clone of another URL), `SyncBaseStore.Clear()`, remember the new URL (or delete the marker), log "Sync state cleared: the repository changed". The next run then asks the join question again. Because the marker is on disk, a URL changed just before quitting is reset at the next start. A clone that cannot be moved (a file open in it) fails the run with that line and nothing changes.

**Options › Sync** (`Screens/OptionsSyncSection`, included last by `OptionsScreen` when a `SyncViewModel` is registered). Repository (a private GitHub repo; the help line says sign-in is git's own and Augram stores no password), This machine, Automatic sync, Status (Sync now + the status line), Conflicts ("2 conflicts with Mac" + Resolve…, shown only while some are pending, through `Field.Visible`), Details (the last run's repairs and notes, shown only when there are some). The two text fields are drafts while typed: every keystroke re-checks (`SyncSettingsRules.UrlProblem`, a blank name) and shows the problem under the box in `TextBlock.error`; leaving the box (or a click elsewhere, `ClickAwayFocus`) or Enter commits a valid draft as one `SettingsStore.SetSync`, Escape reverts. So a URL is never applied half-typed (each new URL resets the state). A stored value changed elsewhere replaces the draft; one being typed survives unrelated settings changes. Status lines: "Off: paste a repository address above…", "Syncing…", "Paused: choose how to join (Sync now asks again).", "Paused: Mac uses a newer Augram. Update this machine (pull, rebuild, restart) to resume.", "Not synced yet.", "Up to date (last synced 14:32).", "Last synced 14:32: 3 commands changed from Mac.", "Sync failed at 14:32: <error line>".

**Join dialog.** `SyncPrompter` listens to the service and, when a finished run's report is `NeedsJoinChoice` (once per report, one dialog at a time), asks `ISyncJoinPresenter` on the UI thread; the answer runs `SyncService.Join`, Cancel leaves sync paused. `SyncJoinPresenter` shows `SyncJoinViewModel.Declare()` in the shared `FormDialog` (680 px wide), modal to the main window when it is open, otherwise as a window of its own (the start-up run usually finds Augram in the tray). The form: the machines already in the repo, newest first ("PC-HOME: Last written 7 Oct 07:40 · 105 gestures · 9 groups · 212 commands"); "Join by" with **Use the synced settings on this machine (recommended)** (default) and **Merge with this machine's settings**; a "What happens" line for the selected one (replaced by the newest machine's, previous file kept as a backup / both kept, items imported separately on each machine appear twice). Confirm is "Join".

**Conflict dialog.** Resolve… calls `ISyncConflictPresenter.ResolveAsync(pending)`; Apply returns every conflict with its choice and `SyncService.Resolve` runs them on the worker, then syncs. `SyncConflictPresenter` builds a `SyncConflictsViewModel` against the stores (names for the summaries) and shows `SyncConflictWindow`: the summary line, a help line, the `SyncConflictList` component and Cancel / Apply. One `SyncConflictRow` per conflict (row rule: `Border.row` + `Grid.row-line`): name and "Gesture · with Mac", this machine's and the other machine's version side by side (a gesture as two `GestureGlyph.row-glyph`, anything else as a one-line summary or "deleted"; a category reads "Personal · Windows only" when its Use on is set), and a choice dropdown, Keep mine by default. Keep both is offered only for a gesture or a command present on both machines (`SyncConflictsViewModel.Allowed`). Columns: `SyncConflict.ItemColumn` / `ChoiceColumn` tokens; theme in `Themes/Wireframe/Sync.axaml`.

**Tray and health.** `SyncTrayItem` adds Sync now to the tray menu while a repository is set (disabled during a run) and a short status to the tooltip ("sync paused: Mac uses a newer Augram" for `NeedsUpdate`). `SyncHealthContributor` fills `HealthSnapshot.LastSyncOutcome` / `LastSyncAt`; Diagnostics › Health shows "Last sync: UpToDate at 14:32:05", or "Paused (Mac uses a newer Augram) at 14:32:05".

**First sync, per machine.** Paste the repo's https URL into Options › Sync › Repository and leave the field. The worker clones it into `<config>/sync/repo` (Git Credential Manager's sign-in window on Windows; the Keychain helper or `gh auth setup-git` on macOS, `../Augram.Sync.Git/README.md`). The first machine finds no other file: "Up to date", and its file is pushed. The next machine finds it and asks the join question.
