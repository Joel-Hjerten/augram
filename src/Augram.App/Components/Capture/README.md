# Capture

Controls that take input from the whole system through a port, falling back to their own window without the engine (`--no-engine`). The ports come from `ComponentPorts` unless the control's own property is set (tests, gallery); the engine adapters (`EngineKeyCapture`, `EngineButtonCapture`) live in `Hosting/`. Gallery page: "Capture fields".

| Type | Job |
|---|---|
| `HotkeyCaptureBox` (+ `.SingleKey`) | The hotkey field (F5): Capture or a click arms `IKeyCapture` (every key comes here, Win+L included); commit is mouse-only (Accept, a press outside, the window losing activation); Clear commits no key; every exit gives the keyboard back first; the engine's own release (10 s idle, hook reset) keeps what was pressed and says why. One-key mode (`SingleKey`): a hold key or an input; modifiers refused, with the host's reason from `KeyProblem` (Core's rule). `LayoutId`: the keyboard layout the key is named by (a per-layout row; null, the active one); `KeyboardLayouts`: the port asked (the form's own, else `ComponentPorts`, else `HotkeyText`'s). |
| `HotkeyRecorder` | Pure "modifier set + one key" logic, right-hand modifiers kept. |
| `CaptureWindowWatch`, `AvaloniaKeyMap` | What a capturing field watches on its window (presses outside, deactivation, and the window's keys in the fallback), and Avalonia keys to Core's. |
| `ModifierToggle` | A modifier's check box with its "R" (right-hand) toggle. |
| `HotkeyChoices` | The editors step forms put beside the field: `Keys` (every key by its name here), `ModifierToggle(flag, …)`, `HeldKeys(…)` (a row of modifier boxes), `Modifiers` in press order. The Hotkey, Remap and Scroll forms use it; no form builds these itself. |
| `IKeyCapture`, `IButtonCapture` | The ports; `Begin` returns null when nothing can capture. |
| `ButtonDetector` | Detect-to-assign for a mouse button (a hold remap command's Add button…): the next press anywhere (the engine) or on its window (fallback, the press marked handled); gives up after 5 s and says so. |

## Hotkey capture (F5)

`Components/Capture/HotkeyCaptureBox` shows the combination ("Ctrl+Shift+T" or "No key set"). Capture, or a click on the field, arms `IKeyCapture`, so every key press goes to the field and none to the OS (Win+L, Alt+Tab, Esc and PrintScreen included); the field shows what is held live and the latest combination wins. Commit is mouse-only: Accept, a pointer press anywhere outside the field, or the window losing activation keep the latest combination and raise `Committed`; Clear commits no key. Every exit gives the keyboard back first; unloading keeps nothing. When the engine ends the capture itself (10 s idle watchdog, hook reset, stop) the field keeps what was pressed and says why. `EngineKeyCapture` wraps `EngineHost.CaptureKeys` and marshals to the UI thread; `FormServices.Publish` makes it the application's `ComponentPorts.KeyCapture` while the engine runs, because step forms are built by scan without services. Under `--no-engine` nothing is published and the field reads its own window's key events (`CaptureWindowWatch`, `AvaloniaKeyMap`) and says Win+L, Alt+Tab and PrintScreen cannot be recorded that way. `HotkeyRecorder` holds the pure "modifier set + one key" logic. **Right-hand modifiers are kept** (F5, Joel 2026-10-07): the recorder remembers which physical modifier keys are held, and one held on the right only becomes `RightHand` ("RAlt+F9", "RCtrl+RShift+P"); held on both sides, or known only from the event's reported mask (held since before the capture), it is plain. The field's `RightHand` property and `HotkeyCommittedEventArgs.RightHand` carry it; Clear resets it. **Key names follow the active keyboard layout** (plan 0011 decision 6): the field's text and `HotkeyChoices.Keys` are `HotkeyText`'s, which asks the `IKeyboardLayouts` port `FormServices.Publish` set at startup; on a layout change the composition root re-publishes `ComponentPorts` (the same instance), and the field re-reads its text on that resource change, while the Hotkey form re-declares itself so its dropdown and its per-layout rows follow (`Components/Steps/README.md`). **A per-layout row names its keys by its own layout** (Joel, 2026-10-13, first round): the form sets the field's `LayoutId` to the row's layout and `KeyboardLayouts` to its port, and the set text, the live text while capturing and the one-key text all go through `HotkeyText` with that id, so the Swedish row reads "Cmd+Å" and the ABC row "Cmd+[" whatever is active; the main field (shown only with the switch off) has no id and follows the active layout. On an AltGr layout (Joel's Swedish one) Windows reports AltGr as a synthesised LeftControl plus RightAlt, so pressing AltGr+F9 records "Ctrl+RAlt+F9"; that is accepted, since replaying it sends what Windows saw. In the form's hand editor each modifier is a `ModifierToggle` (`Components/Capture/`; the forms build it through `HotkeyChoices.ModifierToggle`): its check box plus a small "R" toggle (tooltip "Right-hand key"), enabled only while the modifier is on; any change emits the normalised step (`HotkeyStep.Normalized()`), so turning a modifier off drops its right-hand bit. The theme of the field and the toggle is in `Themes/Default/Forms.axaml`. **One-key mode** (`SingleKey`, `HotkeyCaptureBox.SingleKey.cs`; plan 0002 step 4: a hold key, a hold remap command's key input): the field takes one key and shows it alone ("Space"); modifiers held with it are dropped; a key it refuses is not recorded and the status line says why: Ctrl, Alt, Shift and Win (Opt, Cmd on a Mac) always, in the host's words when `KeyProblem` gives them (Core's `HoldRemapRules.HoldKeyProblem` / `InputKeyProblem`, so the field words no rule of its own), and any other key `KeyProblem` refuses (an input that is the hold key). Fn never reaches the field.
