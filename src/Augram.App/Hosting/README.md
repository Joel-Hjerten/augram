# Hosting

Process-level services and the composition: what runs for the life of the process, outside any window. `CompositionRoot.cs` (one folder up) calls the modules; nothing here is a view or a view model. This page says what lives where, which type to reach for and the order things start and stop in; then the long story of each part, with Joel's decisions: packaging, version and channel, start at login, the hidden launch, one Augram at a time, the engine's slices of the composition root, and how settings flow (the tray itself is in `Tray/README.md`).

## What lives here

| Folder | Types |
|---|---|
| `Modules/` | One module per slice of the composition root, each `Register` (only registers) and, where the slice starts something, `Start` (UI thread, resolves and starts): `ConfigModule` + `ConfigModuleOptions` (the config session and its three stores), `PlatformModule` (the Windows or macOS adapters, or the null objects), `EngineModule` + `EngineModuleOptions` (input source and simulator, overlay, `EngineHost`, the engine links and captures, `MainWindowOpener`), `DialogsModule` (the confirmation, the take-over's confirmation, the form dialog: registered once for every slice), the tabs' `GesturesModule`, `CommandsModule`, `IgnoredModule`, `OptionsModule`, `DiagnosticsModule` (each with its tab's `NavEntry`), `TransferModule`, `SyncModule` + `SyncModuleOptions` (sync's runtime is in `Sync/`), and `FormServices` (publishes the `Components/ComponentPorts` resource). A module never re-registers another slice's store or presenter; it resolves it. |
| `Launch/` | What this launch is: `LaunchArguments` (the switches, parsed once in `Program.Main`), `AppInfo` + `AppChannel` (version, commit, Dev or Release), `AppPaths` (config folder, logs), `EngineKillSwitch` (`--no-engine`, `AUGRAM_NO_ENGINE=1`), `LaunchVisibility` (a hidden launch). |
| `Startup/` | Start at login (F7): `StartAtLoginLink` (keeps the OS registration in step with the setting, owns its note), `AppState` (the tray's and Options' flags projected over the settings and the link), `StartupPolicy` + `StartupAction` (who wins). |
| `Instance/` | One Augram at a time (A10): `InstanceListener` (the running side: mutex and pipe, its events), `InstanceClient` (the asking side: `Send`, `SignalExisting`), `InstancePipe` (the names and options both agree on), `InstanceStartup` + `InstanceStartupStep` (the decision at launch, the only caller of both), `InstanceIdentity`, `InstanceRequest`, `InstanceRequestEventArgs`, `PeerAnswer`, `InstanceProtocol` (the wire format), `NamedMutexOwner`. |
| (top) | Engine links: `EngineSettingsLink` (settings and mapping changes into the running engine), `EnginePauseState` (the ignore list's pause, for the tray), `StrokeButtonDetection` (detect-to-assign for the stroke button), `EngineKeyCapture` and `EngineButtonCapture` (the engine's captures as the components' `IKeyCapture` and `IButtonCapture`). The window: `MainWindowFactory` (the main window with its look, for the app and `tools/UiShots`), `MainWindowOpener` (show the window; the Open app step's "This app"). Threads and timers: `UiThread`, `OneShotTimer`, `SettingsFollower<T>`. Process-wide behaviours: `ClickAwayFocus` (a click outside, or Enter in a single-line text box that did not handle it, takes the focus away), `ControlCharacterInput` (text input of control characters only, as macOS makes of an unhandled Escape, is dropped before any text box inserts it), `MacDockPresence`, `HiddenWindowReset` (what hiding the main window resets: every list's search text, plan 0009 decision 8; one call per view model, followed from `App.StartDesktop`). Small services: `IClipboardText`/`AppClipboard`, `AppHealthContributor`. |

## Which type for which job

| Job | Use | Notes |
|---|---|---|
| Read a launch switch | `LaunchArguments` (registered; `LaunchArguments.Current` for a static reader) | Parsed once in `Program.Main`. `AppPaths.ConfigFolder` and `EngineKillSwitch.IsSet()` are one-line readers of it. A new switch is a property and a line in `Parse`, with its rule beside the type that owns its meaning. |
| Give a component built without services a port | `Components/ComponentPorts` via `FormServices.Publish` | One application resource (`ComponentPorts.ResourceKey`): display modes and window system always, the key capture and button capture only while the engine runs. A component reads `ComponentPorts.Near(this)` (or `OfApplication()` before it is in a window); its own explicit property wins. |
| Add a tab | A module's `NavEntry`, listed in `Navigation/AppNavigation.Build` | Its view models registered in the same module's `Register`. |
| Show the main window | `MainWindowOpener.ShowNow` (UI thread) | The tray's Open and double click, a second launch, a macOS reopen; `Open()` posts it for the engine's Open app step once `App` has attached it. |
| Hand work to the UI thread from any thread | `UiThread.Post` | The one marshal: `CompositionRoot` passes it to `ConfigModuleOptions.Marshal`, `EngineModuleOptions.Marshal` and `SyncModuleOptions.Marshal`, and every class taking an `Action<Action>` marshal defaults to it. Never write `Dispatcher.UIThread.Post` for this. |
| React to a store change that may come from a worker | `UiThread.RunOrPost` | Runs at once on the UI thread (edits, headless tests), posts otherwise. View models get it through `ViewModels/StoreViewModel.OnStoreChanged`; the training session gets it from `GesturesModule`. |
| Wait for the UI thread from a worker | `UiThread.IsCurrent` + `UiThread.Invoke(function, cancel)` | Only `Sync/SyncStoreThread` does this. |
| Run something once after a delay (debounce, timeout, poll) | `OneShotTimer.Schedule(delay, action)` | A `System.Threading.Timer` per request, the action through the timer's marshal (none: the timer thread). Dispose the result to cancel; restart = dispose and schedule again. A request disposed after its timer fired but before the marshalled action ran is skipped. Users: the config save (250 ms, marshalled to the UI thread), sync's poll and change timers (no marshal), stroke-button detection's 5 s timeout. |
| Follow part of the settings and push what moved | `SettingsFollower<T>(settings, select, apply)` | Remembers the last selected value; on a change that leaves it different, `apply(last, next)`. Dispose to unsubscribe. Users: `EngineSettingsLink` (whole `Settings`), `StartAtLoginLink` (`StartAtLogin`), `AppState` (`GeneralSettings`), `CommandsViewModel` (stroke button, drag distance). |
| Animation or UI-only timing inside a control | `DispatcherTimer` / `Dispatcher.UIThread.Post` with a priority | Components keep these (a focus after layout, a render frame); they are not marshals. Each is allowlisted by file in `Architecture/OneHomeHostingTests` ([one-home guards](../../../docs/reference/one-home-guards.md)); a new one is added there with its reason. |

## Startup and shutdown order

As the code runs today (`Program.Main`, `App.axaml.cs`, `App.Launch.cs`). `EngineModuleTests` pin the engine part; changing an order here is a behaviour change, not a refactor.

**Start.**

1. `Program.Main`: `VelopackApp.Build().Run()` first (the installer's hooks exit here).
2. `LaunchArguments.Parse(args, AUGRAM_NO_ENGINE)` becomes `LaunchArguments.Current`.
3. `InstanceStartup.Begin()`: takes the name (`InstanceListener`: the `augram-instance-mutex` and `augram-single-instance` threads) or asks the running Augram through `InstanceClient` and exits, or leaves the choice to `App` (a different build).
4. `RunningPlatform.UseThisMachine()`.
5. `CompositionRoot.Build`: registers only; nothing is created yet. Order: diagnostics, `AppInfo`, `LaunchArguments`, `StartAtLoginLink`, `AppState`, clipboard, then `DialogsModule`, `ConfigModule`, `PlatformModule`, `EngineModule`, `GesturesModule`, `CommandsModule`, `IgnoredModule`, `TransferModule`, `SyncModule`, `OptionsModule`, `DiagnosticsModule`, the tray, navigation, `MainWindowViewModel`, `MainWindow`. Registration order matters only where two registrations would compete, and none does.
6. Avalonia starts: `App.Initialize` (XAML, the theme, `ClickAwayFocus.Register`, `ControlCharacterInput.Register`), then `OnFrameworkInitializationCompleted`: explicit shutdown mode; on macOS the launch event is observed; a launch that must choose (`InstanceStartup.NeedsChoice`) resolves only the take-over's confirmation (keyed `ConfirmPresenter.AloneKey`), asks, and either quits or goes on to `StartDesktop` once it holds the name.
7. `App.StartDesktop`, in this order:
   1. `IEventLog` (the first service created, so the last disposed), `AppInfo`, `LaunchArguments`; `LaunchVisibility.AtStart`; the `App started` line; the take-over notes; `AppHealthContributor`; in Debug, `--gallery` picks the first tab.
   2. `MainWindowFactory.Create`: `AppearanceLink.Follow` (resolving `SettingsStore` creates the `ConfigSession`: `Configuration loaded`, the placeholder upgrade, a first run's file), then `MainWindow` (its view model, the navigation registry, the first tab's view models), the look attached. Then the dialogs' backdrop handler, `HandOver` of the window to the lifetime (now, or as the main loop's first job), on macOS the Dock icon and `MacDockPresence`.
   3. `MainWindowOpener.Attach`.
   4. `EngineModule.Start`: under the kill switch one `Engine disabled by flag` line and nothing else (no hook, no overlay, no host). Otherwise: on macOS the Accessibility line; `EngineHost` (its ports: input source, simulator, the trail overlay created hidden, the adapters, the training session as `Intercept`); `EngineSettingsLink`; `AppState` with its `StartAtLoginLink`, then `StartAtLoginLink.SyncStartupRegistration`; `host.Start()` (the hook and the `augram-engine-worker`, `augram-command-executor`, `augram-ignore-watch` threads); `EnginePauseState.Follow(host)`.
   5. `FormServices.Publish` (the captures only when the engine runs).
   6. `SyncModule.Start` (also under `--no-engine`): `SyncPrompter`, `SyncHealthContributor`, `Sync ready`, `SyncService.Start` (the `Augram sync` thread; its first run is the start-up sync).
   7. `AppTray` resolved (created here: `AppState`, `SyncService`, `EnginePauseState`).
   8. The listener's events (`Introduced`, `ShowRequested`, `QuitRequested`), the macOS reopen, the `Exit` handler.
   9. macOS: wait for the launch event (3 s cap); otherwise `OpenAsLaunched`.
8. The lifetime shows `MainWindow` if it was handed over at once, and runs the main loop.

**Stop.** Quit (the tray, or another Augram's Quit through the listener) shuts the lifetime down:

1. `Exit`: the `App stopping` line, then `AppTray`, `AppHealthContributor` and the macOS launch event are disposed.
2. `Program.Main`'s `using` disposes the service provider: singletons in reverse order of creation. So the tray (already disposed: a no-op), the sync service (before the config session flushes; a run on its thread is abandoned), the engine host (the hook and its threads stop), the overlay, then the config session flushes a pending save, and the event log drains last.
3. `InstanceStartup` disposes the `InstanceListener`: it stops listening, then releases the mutex. Last, so a launch taking over starts only after this process has let go of everything.

## Rules

- Tests never get the real UI marshal by accident: a test that builds a module passes `Marshal = action => action()` (or a recording one); view-model tests run on the headless UI thread, where `RunOrPost` runs at once.
- `ConfigSession` stays single-writer: its save timer's marshal is the UI thread's.
- A module's tests register the siblings it resolves (`tests/.../Support/TabServices.AddSiblings` for the tabs); no module falls back to a store or presenter of its own.

## Packaging and releases

`Program.Main` begins with `VelopackApp.Build().Run()`: Velopack's Setup, updater and uninstaller start the exe with hook arguments, and that line answers them and exits before the single-instance guard or any UI exists, so it stays first. `node scripts/package.mjs windows|mac` publishes and packs the installer; cutting a release, where the app installs, signing and the macOS Info.plist: [docs/release.md](../../../docs/release.md). Nothing checks for updates yet; when something does, it is a `Hosting/` service registered in `CompositionRoot` around Velopack's `UpdateManager` over the GitHub releases (docs/release.md, "Not built yet").

## Dock, version and channel, start at login, hidden launch, one Augram at a time (F7, A10)

**Dock on macOS (Joel, 2026-10-08).** The Dock icon is there only while the main window is open: `Hosting/MacDockPresence` follows the window's visibility and switches the activation policy (`Platform.MacOS/MacDock`: regular with a Dock icon, accessory without). Closing the window hides it (`MainWindow.OnClosing`, both platforms); on macOS minimizing hides it too, so the window never sits in the Dock without an app icon. Open in the tray menu, a second launch or a reopen (opening Augram again from Finder, Launchpad, Spotlight or the Dock while it runs: `IActivatableLifetime`, `ActivationKind.Reopen`, `App.ShowOnReopen`; 2026-10-10) shows both again; Quit is the only way out. The bundle keeps `LSUIElement` unset, so a launch starts with the Dock icon and the window; a hidden launch (below) drops the Dock icon once it has decided. Windows is unchanged: minimize goes to the taskbar.

**Version and channel (2026-10-08).** The version is one property, `<Version>` in `Directory.Build.props` (0.2.0); the SDK appends `+<commit>` to the informational version from git. The build channel is the MSBuild property `AugramChannel`, `Dev` by default (every local and CI build); the release script passes `-p:AugramChannel=Release`. `Augram.App.csproj` embeds it as `[AssemblyMetadata("AugramChannel", …)]`. `Hosting/Launch/AppInfo` reads both (`AppInfo.Current`, registered in `CompositionRoot`): `Version` (0.2.0), `Commit` (the first 7 characters), `InformationalVersion` (0.2.0+3f1c2ab), `Channel`, `IsDev`, `DisplayName` ("Augram (Dev)" or "Augram"), `Label` (the name and the version, "Augram (Dev) 0.5.1"); a missing or unknown channel reads as Dev, the safe side. Joel's rule: there is no mistaking which build runs. The main window's title is `Label` (2026-10-09: Joel wants the version visible), the tray tooltip starts with it, Options › About shows version, commit and channel (read-only notes), and the first log line of a run is `app` / `App started` with version, commit, channel, theme and OS. Dialogs and the training window keep their own titles.

**Start at login is the installed build's.** In the Dev channel `AppState` never calls `IStartupRegistration` (neither writes nor removes, so the installed build's Run entry survives a dev run and logging in never starts a dev copy) and ignores sets of `StartAtLogin`; `CanChangeStartAtLogin` is false, Options shows the toggle disabled with "Start at login applies to the installed Augram; this is a development build.", and the tray item is disabled. At startup it logs `startup` / `Start at login left to the installed Augram`. The Release channel behaves as below.

**Start at login: the registration, and who wins (2026-10-10).** `PlatformModule` registers `RunKeyStartupRegistration` with `--hidden` on Windows (the Run value is `"<exe>" --hidden`) and `MacLoginItemRegistration` (`SMAppService`) on macOS; the platform READMEs have the details. The port reports a `StartupStatus`, and `Hosting/Startup/StartupPolicy` (pure, tested) says what `StartAtLoginLink` does with it (`AppState` projects its note for Options): the setting wins, so at startup (`StartAtLoginLink.SyncStartupRegistration`, from `EngineModule.Start`) a missing entry (config restored on another machine, a moved executable) or an outdated one (another path, or the bare path without `--hidden` that 0.5–0.7 wrote) is written again, and "off" removes whatever is there. One exception, at startup only: the setting is on but the user turned it off outside Augram (Task Manager › Startup apps; on macOS removed from or not allowed in System Settings › General › Login Items). Then the setting follows the OS (it turns off, `startup` / `Start at login was turned off outside Augram; the setting follows`, Warning) instead of switching it back on behind the user's back, and Options shows a state note under the toggle, the **At login** row, plain text by the Help rule because it must be seen ("Turned off in Task Manager › Startup apps."; "Waiting for approval in System Settings › General › Login Items." while macOS waits after a tick; "Could not change it; Diagnostics › Log says why." after a failure). Ticking it in Augram afterwards means on: Windows clears Task Manager's switch-off, macOS registers again. Every startup logs `Start at login checked {setting=… status=…}`, every change `Start at login registered|removed {was=… now=…}`; failures (`IOException`, `UnauthorizedAccessException`, `SecurityException`, `StartupRegistrationException` with the OS's text) are logged as `Could not read|change start at login` and never thrown. The default stays off on a fresh install (requirements F7).

**Hidden launch (2026-10-10).** A launch with `--hidden` (the Windows Run entry passes it; anyone can) or, on macOS, a login-item launch starts in the tray and menu bar only: no window, and on macOS no Dock icon; the engine, sync and tray start as usual. `Hosting/Launch/LaunchVisibility` (pure, tested) decides and names the reason, which the first line logs: `App started {… hidden=true reason=--hidden}` (or `hidden=false`; on macOS `hidden=pending`, then `Launch window decided {hidden=… reason=login item event=aevt/oapp prdt=lgit}`). How the window is kept from showing (`App.Launch.cs`): Avalonia 11.3's `ClassicDesktopStyleApplicationLifetime.Start` shows `MainWindow` once, after `OnFrameworkInitializationCompleted` and right before its main loop (`StartCore`: the `Startup` event, `MainWindow?.Show()`, `MainLoop`), with no switch to skip it, so a hidden launch hands the window to the lifetime as the main loop's first job (`DispatcherPriority.Send`) and that one show finds none; a take-over launch (`ChooseThenStart`) starts after it and shows the window itself unless hidden. On macOS the login-item answer comes from the launch event inside `[NSApp run]` (`Platform.MacOS/Startup/MacLaunchEvent`, observed from `OnFrameworkInitializationCompleted`, before the loop), so every macOS launch defers the window to that answer: no flash on a login launch, and a normal launch shows its window within milliseconds of the loop starting (after 3 s without an answer it shows it anyway, `App.LaunchEventTimeout`). A later launch by the user shows the window as before: the single-instance guard's Show on Windows (and for a second process on macOS), a reopen on macOS. Checked on Windows by Joel (list below); macOS's list is in the Platform.MacOS README, "Start at login on macOS".

Windows check list (installed build from this branch; Joel):

1. Install it, open Options › General and tick Start at login. The log (`%APPDATA%\Augram\logs`) says `startup` / `Start at login registered {was=… now=Registered}` (`was=Outdated` when an older build had registered the bare path).
2. In a terminal: `reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v Augram` shows `"C:\Users\<you>\AppData\Local\Augram\current\Augram.exe" --hidden`.
3. Task Manager › Startup apps lists Augram as Enabled.
4. Sign out and sign in again: Augram's tray icon appears and no window opens. The log has `App started {… hidden=true reason=--hidden}` and `Start at login checked {setting=true status=Registered}`.
5. Double-click the Augram shortcut: the window opens (`Asked to show the window by another launch`).
6. Task Manager › Startup apps › Augram › Disable, then Quit Augram from the tray and start it again: Options shows Start at login off and "At login: Turned off in Task Manager › Startup apps."; the log says `Start at login was turned off outside Augram; the setting follows {status=DisabledByUser}`, and Task Manager no longer lists Augram (the leftover entry is removed). Tick it again: Task Manager lists it as Enabled.
7. Untick it: `reg query …` (step 2) says the value cannot be found.

**One Augram at a time (A10; Joel, 2026-10-08: the installed or a dev build, never both).** Both channels use the same name, `Program.InstanceName`. `Program.Main` calls `InstanceStartup.Begin()` before building anything:

1. `InstanceListener.TryAcquire` takes the mutex (per user; per logon session on Windows) and starts the pipe listener → `Run`.
2. Taken: it sends Hello with its identity (`InstanceIdentity`: channel, version, commit, executable path) and gets the running one's back.
   - Same channel and same executable (a rebuilt copy at the same path included) → it sends Show (reason "same install"), the running one shows its window, this launch exits (the old behaviour).
   - A different channel or executable → `Choose`: `Program` starts Avalonia, and `App` runs `InstanceStartup.ChooseAsync` before resolving anything else, so no engine, hook, overlay, tray or sync exists in this launch yet. The take-over's `IConfirmPresenter` (`Dialogs/ConfirmPresenter.Alone()`, registered under `ConfirmPresenter.AloneKey`: the shared `ConfirmDialog` shown without an owner, centred on the screen) asks "Augram 0.2.0 (installed) is already running. Quit it and start Augram (Dev) instead?" (two dev copies: "…is already running from another folder…" with both paths) with **Quit it and start this one** / **Cancel**. Confirm sends Quit and waits up to 10 s for the mutex; the running one answers, then shuts down as the tray's Quit does (engine stops, config flushes, sync abandons a run on its background thread, `Program` releases the name last), and this launch starts and shows its window. On timeout it says "…did not quit within 10 seconds. Quit it from its tray icon, then start Augram (Dev) again." and exits. Cancel sends Show (reason "take-over cancelled") and exits.
   - A hidden launch (`--hidden`, `InstanceStartup.IsHiddenLaunch`, 2026-10-10) only says hello and exits, whichever build answers: it never shows the running one or asks about a take-over (the Run entry fires some seconds after sign-in, maybe after the user started Augram).
   - An Augram from before identities (0.1) → it was shown by the connection itself; this launch exits.
   - No answer within 2 s (the running one is starting, stopping or stuck) → it waits up to 3 s more for the mutex, then runs or exits.

The pipe protocol (`InstanceProtocol`) stays compatible both ways. A request is the byte 2 and one JSON line (`request`, `reason`, `channel`, `version`, `commit`, `path`); every answer is the listener's identity as one JSON line. The listener treats anything else (0.1's one byte, a connection that closes or breaks before a full request, an unknown verb) as Show: the connection is the request, and a broken pipe on that read must not lose it (a Windows CI run did, 2026-10-07). A 0.1 listener is inbound only, so Windows refuses the two-way connection and `Send` asks it the old way (`SignalExisting`); off Windows it reads one byte and closes, which reads as `Older`. On Windows the pipe is `CurrentUserOnly` both ways (pipe names are machine-wide there), so another user's Augram can never be shown or quit. Off Windows a pipe is a domain socket that lives only while a server stream does, and a client that connects while the previous request is being served waits in the socket's queue: the listener makes the next server stream before it lets go of the served one, or that client is dropped (the Show or Quit after a Hello was lost on macOS, 2026-10-08). The mutex is held by its own parked thread (`NamedMutexOwner`): a mutex belongs to the thread that took it, and the take-over waits for it from the UI thread without blocking. `Dispose` stops the listener first, then releases. Logging: the running side logs `app` / `Another Augram is starting`, `Asked to show the window by another launch` and `Asked to quit by another Augram` with the asker's identity and reason; the launch that takes over logs `Took over from another Augram` (who, and how long it waited) right after `App started`. A launch that exits writes no log of its own, because two processes appending to one daily file would clobber each other's lines; its side is in the running one's lines. Tests use real mutexes and pipes under a unique name per test (`Support/InstanceTesting`) and fake the dialog (`FakeConfirmPresenter`).

## ConfigModule, PlatformModule, EngineModule (the engine's slices of the composition root)

`CompositionRoot.Build` calls `ConfigModule.Register`, `PlatformModule.Register` and `EngineModule.Register` after the diagnostics services; `App.StartDesktop` calls `EngineModule.Start(services)` once the main window exists, then `FormServices.Publish`. Together they add: `ConfigSession` over a `FileConfigStore` at `AppPaths.ConfigFolder` (load notices go to the log as source `config`; a first run writes the defaults and starter gestures at once; saves are debounced by a `OneShotTimer`, a `System.Threading.Timer` whose callback is marshalled to the UI thread so the session stays single-writer); `SettingsStore` and `GestureLibrary` from the session (`ConfigModule`); `IClock`, the input source (`SharpHookInputSource`, or the factory in `EngineModuleOptions.InputSource`, which tests set to a fake so no hook is installed) and `SharpHookInputSimulator`; the Platform adapters (`Win32CursorProbe` or `MacCursorProbe`, `Win32SystemEvents` or `MacSystemEvents` as `ISystemEvents` (session, power, display and, for hold remaps, a new foreground; both are created when the host is resolved in `Start`, on the UI thread, which on Windows pumps the foreground WinEvent hook and on macOS is the main thread the observers need), `OverlayWindowStyle`, `RunKeyStartupRegistration` (with `--hidden`) or `MacLoginItemRegistration` as `IStartupRegistration`, the window system and operations, `Win32ProcessLauncher` or `MacProcessLauncher` as `IProcessLauncher` for the Run step, `Win32Clipboard` or `MacClipboard` as `IClipboard` for the Clear clipboard step; `PlatformAdapters = false` swaps in the null objects); `TrailOverlayWindow` as `IStrokeTrail`, or `NativeTrailOverlay` when the platform registered an `ITrailSurface` (macOS: `MacTrailPanel`); `EngineHost` with gestures = `GestureLibrary.All`, recognition options = `Settings.Current.Recognition`, and the initial stroke button, thresholds, ignore key and enabled flag read from the store; `EngineSettingsLink` (settings, and every mapping change as `EngineHost.MappingChanged`, so an Exclusions-tab edit reaches the ignore-list watch at once); `EnginePauseState`; `StrokeButtonDetection`. `Start` returns after one log line when `EngineKillSwitch` is set (`--no-engine` or `AUGRAM_NO_ENGINE=1`); otherwise it resolves the host (which constructs the overlay on the UI thread, hidden), subscribes the link, syncs start-at-login with the OS (the installed build only; a Dev build leaves it alone), starts the hook, and links `EnginePauseState` to the host. The headless test app builder only calls `Build`, never `Start`. Disposal runs in reverse through the service provider: the host stops the hook, the session flushes a pending save, the log drains last.

## How settings flow

`SettingsStore` is the only mutable owner of `Settings` (ADR-0002 §5a). Writers: `AppSettingsViewModel` setters (one store change each; the Options page has no Undo / Redo row since 2026-10-07), `AppState.Enabled` / `StartAtLogin` (tray and Options), and `StrokeButtonDetection` (F1 detect-to-assign: `EngineHost.CaptureNextButtonPress`, 5 s timeout). Readers: `EngineSettingsLink` pushes the stroke button, ignore key, thresholds and enabled flag into `EngineHost` on every `Changed` (undo included); the recognizer reads `Recognition` through a delegate per stroke; the overlay reads `Trail` at every `Begin`; `AppState` applies `StartAtLogin` to `IStartupRegistration` as `StartupPolicy` says (Release channel only; at startup it may turn the setting off to follow an "off" made outside Augram) and raises `PropertyChanged` for the tray. The view model raises `PropertyChanged` with an empty name on every store change, so every `DelegateBinding` on the page refreshes at once. The config folder is read-only on the page; `--config-folder <path>` (or `=path`) changes it (A17 minimal).
