# Augram.Platform.MacOS

macOS implementations of the same Core ports as `Augram.Platform.Windows`, through CoreGraphics, the Accessibility API (`AXUIElement`) and a handful of AppKit calls via the Objective-C runtime. Started 2026-10-07 on Joel's Mac (Apple silicon, built-in Retina display at 2x plus an external display at 1x, "Displays have separate Spaces" on).

**May reference:** `Augram.Core` only. AppKit / Accessibility interop goes here and nowhere else.

**Must never contain:** Avalonia, SharpHook, business rules, or Windows types.

## Ignore list on macOS (2026-10-09, not yet run on a Mac)

The engine's ignore-list watch (`src/Augram.Engine/README.md`, "Ignore list") runs the same code on both platforms; only the two cheap keys above are Mac-specific. An ignored app matches on its macOS executable names, or on the known-app guess from its Windows names (`Core/Mapping/KnownApps`); an entry with only Windows names and no guess (`vmware.exe`) matches nothing on a Mac, and while no active entry can match here nothing is watched at all. The Mac session must verify:

1. Over an ignored app (Blender, or any app added on the Ignored tab by its macOS name), a right-drag reaches the app untouched: no trail, the app's own drag works, and the wheel while the button is held scrolls the app.
2. A "disable while focused" app (VMware Fusion, executable `VMware Fusion`; or TextEdit for the test) pauses Augram while it is frontmost: the log says `Paused while an ignored app has focus`, the menu-bar tooltip says "Augram (paused: … is focused)", and gestures work again (`Resumed: …`) within about 200 ms of another app coming to the front.
3. Idle cost: with the ignore list watched and the pointer still, Activity Monitor shows Augram near 0% CPU (the watch asks `Ax.FocusedApplicationPid` every 200 ms); while moving the pointer it stays low (the window list is read at most every 250 ms, plus once per window entered).
4. `Ax.FocusedApplicationPid` answers without the Accessibility prompt beyond the one Augram already needs, and gives Augram's own pid when its window is in front. **Found 2026-10-09: it crashed.** With Augram in front, the system-wide query is answered in-process on the calling thread through AppKit and Avalonia's window; on `augram-ignore-watch` that was EXC_BAD_ACCESS in `-[AvnWindow automationPeer]` (three crashes at start of the installed 0.5.1, right after a take-over showed the window). The system-wide query now always runs on the main thread (`Interop/Ax.Focus`).
5. The real executable names of the apps Joel ignores on the Mac (`Resolve` for DaVinci Resolve, `VMware Fusion`, `Blender`), so `KnownApps` can learn the pairs.

Not built yet: the placement operations. `ISystemEvents` is `MacSystemEvents` since 2026-10-10, `IStartupRegistration` is `MacLoginItemRegistration` since 2026-10-10 (both below).

## Start at login on macOS (2026-10-10, compiled, not yet run on a Mac)

Ticking Start at login (Options › General or the menu-bar menu) in the installed Augram registers Augram.app as a login item (`MacLoginItemRegistration`); a development build never touches it (App README, "Start at login"). A login item registered this way takes no arguments, so the App cannot ask for a hidden launch as the Windows Run entry does with `--hidden`; it detects one: `MacLaunchEvent` reads the launch Apple event when launching finishes, and a login-item launch starts with no window and no Dock icon, in the menu bar only (App README, "Hidden launch"). To avoid a flash, on macOS the App never lets Avalonia show the window at start: it shows it itself once the launch event has decided (within milliseconds of `[NSApp run]`; after 3 s without one it shows it anyway). Opening Augram again from Finder, Launchpad, Spotlight or the Dock while it runs reaches it as a reopen (`IActivatableLifetime`, `ActivationKind.Reopen`), which shows the window.

What macOS reports, and who wins: `enabled` is registered. `requiresApproval` (registered, but the user must allow it in Login Items) and `notFound` (Apple: "couldn't find this service"; developers report it once the user removed the app from Login Items) count as the user's "off": if the setting is on, Augram's next start turns the setting off and says so on Options ("Removed in …" / "Not allowed in System Settings › General › Login Items."), instead of registering again behind the user's back (Apple DTS advises the same). `notRegistered` with the setting on (a config copied from another Mac) registers again. Ticking it in Augram registers again in every case; while approval is pending Options says "Waiting for approval in System Settings › General › Login Items."

**Unverified, needs Joel's Mac:** that `register` works from the signed bundle and lists Augram under Login Items; that a real login launch carries `lgit` in the launch event (this is how Electron detects it, unverified for Augram); that the Dock icon, present from launch because the bundle leaves `LSUIElement` unset, disappears at the decision (a brief Dock icon at login is expected; `LSUIElement: true` in `package.mjs` would avoid it, Joel's call); which status macOS 26 reports after Augram is removed from, or switched off in, Login Items; and that a reopen shows the window. On macOS 15 and later the pane is called "Login Items & Extensions".

Check list (installed build, with the log open at `~/Library/Application Support/Augram/logs/`):

1. Install the signed `.pkg` built from this branch (release.md) and start Augram from Applications. The log says `App started {… hidden=pending}`, then `Launch window decided {hidden=false event=aevt/oapp prdt=-}` (or `event=none`); the window opens as before, with the Dock icon.
2. Tick Options › General › Start at login. The log says `startup` / `Start at login registered {was=NotRegistered now=Registered}`; macOS may show a "Login Item Added" notification. No "At login" line appears on Options (one saying "Waiting for approval…" means macOS wants approval: say so).
3. Open System Settings › General › Login Items (& Extensions): Augram is listed under Open at Login.
4. Log out and log in again (Apple menu › Log Out). Augram appears in the menu bar with no window and no Dock icon (a Dock icon that shows briefly and goes is expected; say how long). The log has `App started {… hidden=pending}`, `Launch window decided {hidden=true reason=login item event=aevt/oapp prdt=lgit}` and `Start at login checked {setting=true status=Registered}`.
5. Double-click Augram in Applications (or Spotlight): the window opens with the Dock icon (`Asked to show the window by a reopen` in the log). Close it: it goes back to the menu bar.
6. In System Settings › Login Items, remove Augram (−). Quit Augram and start it again: the log says `Start at login was turned off outside Augram; the setting follows {status=…}` (say which status), Options shows Start at login off and "At login: Removed in System Settings › General › Login Items." Tick it again: it is back in Login Items. If instead the restart logs `Start at login registered {was=NotRegistered …}`, this macOS reports a removed item as not registered and Augram added it back: say so.
7. Untick Start at login in Augram: Augram leaves Login Items (`Start at login removed`).
8. If step 4 opened the window, or the log says `prdt=-` at the login launch: report the `event=` text; the detection needs another way.

## System events and hold remaps on macOS (2026-10-10, compiled, not yet run on a Mac)

With `MacSystemEvents` registered, the Mac gets what Windows has had: the hook health monitor logs `System event` for sleep, wake, lock and unlock, and resets the hook's records (and releases anything a hold remap holds) at wake and unlock; the ignore-list watch drops its window keys at wake, unlock and display changes, and checks focus at once when another app becomes active. The Mac session must verify, with the app running from the terminal and the log open (`hold` lines are Debug: set the level on Diagnostics › Log):

1. Start-up: no crash, and the log has `hold` / `Hold remaps watched` once a Blender group with a Space hold remap exists (macOS name `Blender`).
2. Cmd-Tab into Blender and press Space at once: `Foreground hold remaps {app=Blender, keys=Space}` appears within a few milliseconds of the switch (its time against the switch), and the very first Space press is a `Hold`. Cmd-Tab away: the line again with no app, and Space types normally.
3. If step 2 shows the plan arriving only at the 200 ms poll, the Accessibility focus query lags the notification: say so (the fix is to take the pid from the notification's `NSWorkspaceApplicationKey`).
4. Lock the screen (Ctrl-Cmd-Q) and unlock: `System event {kind=SessionLocked}` then `SessionUnlocked` and `Capture reset`; put the Mac to sleep and wake it: `Suspending`, `Resumed`. Two lines for one lock (the session and the screen notifications) are expected and harmless.
5. Change the display arrangement or resolution: `System event {kind=DisplayChanged}`.
6. Quit Augram from the menu bar: it exits cleanly (the observers are removed at disposal).

## Hold remaps: posting on macOS (2026-10-10, plan 0002 step 3a, compiled, not yet run on a Mac)

The spike's recipe (learnings 0005, variant B with the native poster) moved into Augram: Shift and Ctrl around a hold remap's button output are CoreGraphics flagsChanged events with the flags also on the button's down, and while the output is held the engine swallows every physical move and drag and re-posts it as a drag of that output (Engine README, "Re-posted drags"). The Mac session should check, with Blender's Space hold remap (plan 0002 step 5) and the log at Debug:

1. Space + Left orbits, Space + Right pans, Space + Middle and Space + Left + Right zoom; rolling Left → Left + Right → Right → Left mid-drag follows each time.
2. The pointer follows the hand during each drag and stops where the hand does; right after the release plain moves, clicks and drags work everywhere (nothing stuck, no drift).
3. Each drag logs `hold` / `Output released {…, drags=N, dragsFailed=0}` with N in the dozens or hundreds; no `Hold decision mismatch`, no `Hold remap injection failed`.

## Coordinates and identity

- **Units are points, origin top-left of the main display, y down** everywhere this project hands a value out: the hook reports the pointer that way, CoreGraphics window bounds and the Accessibility API use it, and so does Avalonia for screens and window positions. Only `NSScreen` is bottom-left based; `MacRect.FromCocoa` flips it by the main screen's height. `WindowSize` is read as points.
- `WindowIdentity.Handle` and `RootHandle` are both the `CGWindowID` (a macOS window has no child windows to resolve). `ProcessName` is the executable's file name (`Safari`, `Google Chrome`, `Code`), the counterpart of `chrome.exe`; `ProcessPath` is the full path inside the bundle; `ClassChain` is empty; `Title` is null unless the process may record the screen (Screen Recording permission).
- The pointer is a window too on macOS 26: a 28 × 40 "Cursor" window of the window server at `kCGCursorWindowLevel` (2147483630) under the point (measured 2026-10-09: the window finder's crosshair made every drop name WindowServer). `MacWindowPick.At` skips that layer.
- `IsDesktop`: the hit window is below the normal layer (wallpaper, Finder's desktop icons). Window operations refuse the desktop. A smaller window on a higher layer (menu bar, status items) wins over the window behind it, so a gesture there never reaches a window the user was not pointing at. Display-sized windows above the normal layer are skipped: the Dock draws itself in a transparent window as large as its display, and overlay utilities do the same, so they would otherwise swallow every point on that display.
- A window operation finds the window again by its `CGWindowID` among its app's `AXWindows` (`_AXUIElementGetWindow`, private but what every macOS window manager uses); not found → "window gone".

## Threading and permissions

- `MacWindowSystem` and `MacWindowOperations` run on the engine worker / command executor, never on the hook thread: every AX call is IPC to the target app (bounded by the 0.5 s messaging timeout), **except when the target is Augram itself**: then AppKit answers in-process on the calling thread, so it must be the main thread (`Interop/MainThread`). That covers Augram's own elements (`Ax.IsOwn`) and the system-wide focus query, which reaches Augram whenever Augram is in front. `MacScreens` reads `NSScreen` from that thread inside an autorelease pool, and `MacClipboard` clears `NSPasteboard` there the same way; `MacTrailPanel` runs on the UI thread, as AppKit requires.
- Everything that acts (the hook's event tap, injected input, AX calls) needs **Accessibility** (System Settings › Privacy & Security › Accessibility). macOS grants it to the responsible app: Augram once it is an app bundle; during development the terminal or editor that launched it (VS Code here, already granted). Without it the hook fails to install and every window operation fails with "Accessibility permission missing".
- On macOS SharpHook's `KeyTypedEnabled` is switched off (`Engine/Input/SharpHookInputSource`): libuiohook would otherwise resolve each key press to a character with a synchronous trip to the main thread, making every key on the machine wait for the UI thread.
